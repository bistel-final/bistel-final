### 3.1 ①에서 선별하는 artifact hash

① 전체 스키마나 RAG 원문을 승계하지 않고 다음 세 artifact의 검증된 원본만 선별한다.

| artifact | SHA-256 |
|---|---|
| `03_db/01_schema.sql` | `2b0195ba55e2f49fd3af63afccf395568a6aea5c9d008a871462754d4d9f2cb2` |
| `05_scripts/load_documents.py` | `73c30492c6266503fbf6b4f56ce2b5d0b86ba9796f81ab62b1116707e37a2ba7` |
| `04_infra/requirements.txt` | `c531fac10bb950ae05451572dfdbf573638e1702cddf43fe51afdd7d074f0e72` |

`01_schema.sql`에서는 `document`·`document_chunk`와 vector extension 선언만 추출한다.
`load_documents.py`는 그대로 실행하지 않고 다음 adapter 계약을 적용해 재사용한다.

- 입력 경로를 ③에서 만든 corrected RAG source 3종으로 명시한다.
- chunk ID를 `<document_id>:<chunk_schema_version>:<4자리 순번>`으로 결정론적으로 만든다.
- DSN과 대상 DB를 필수로 받고 database allowlist·expected schema·권한을 검사한다. 로컬 기본
  DSN이나 암묵적 fallback은 허용하지 않는다.
- 세 문서의 delete·insert·embedding 저장을 단일 transaction에서 수행한다.
- 같은 source/corrected hash와 chunk ID를 재적재하면 중복 없이 같은 결과가 되는 멱등성을
  보장한다.

## 4. ①의 스키마를 그대로 쓰지 않는 부분

①은 `fdc_alarm`·`fdc_summary`·`dim_*` 10여 개를 포함한 통합 스키마이고, ③은 base 9 table
(`trace_alarm_history`·`summary_alarm_history`·`summary_data` 등)이다. **테이블 이름부터
다르다.** ①에서 가져오는 것은 `document`·`document_chunk` 두 테이블과 `vector` extension
선언뿐이며, 나머지 ① 스키마는 채택하지 않는다.

①의 `agent_run`·`agent_tool_call`·`approval_request`도 쓰지 않는다. Agent Runtime 9 table은
시스템설계서 §3.4가 정의하고 `V5-CM-3.2`가 생성한다.

## 5. 이 문서가 생긴 이유

2026-08-20 B 영역 범위 재검토 중, `load_documents.py`·`bge-m3`·`document_chunk`가 ②·③
어디에도 없어 **"팀이 만든 과설계"로 오판**한 일이 있었다. 실제로는 ①에 실재하는 멘토
제공물이었다. ①이 기준 문서에 등재돼 있지 않아 검증 범위에서 빠진 것이 원인이다.

반대 방향의 착오도 가능하다 — ①에도 RAG 문서와 `master.cypher`가 있으므로, 출처를 명시하지
않으면 구 버전을 정본으로 삼을 수 있다(§3.2의 해시가 전부 다르다).

## 6. 참고 Frontend의 Ontology 화면

③의 `frontend/src/pages/Ontology.jsx`는 **Neo4j Browser를 iframe으로 여는 14줄**이며
로그인 안내 문구(`Login neo4j / password`)를 화면에 노출한다. 즉 **팀이 만들 Ontology 화면의
참고 구현은 존재하지 않는다.**

따라서 화면·API 형태는 팀 설계이고, 지켜야 할 제약은 NFR-02 하나다 — **Neo4j 자격증명을
Frontend에 노출하지 않고 read-only Backend adapter를 경유한다.**
