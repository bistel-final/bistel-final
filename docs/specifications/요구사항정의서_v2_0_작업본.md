### 1.1 개정 목적

신규 배포 자료는 기존 자료와 달리 공개 Fault 정답 라벨을 제공하지 않는다. 따라서 기존
`fault_code` 기반 학습·평가, 51건 Fault 분류 정답, `ACT-0001~0010` 조치 정답 및 4단계
조치 규칙을 폐기하고, 결정론적으로 재현 가능한 규칙 결과와 상태 전이를 중심으로 요구사항을
재정의한다.

### 1.2 요구사항 상태 표기

| 표기 | 의미 | 적용 원칙 |
|---|---|---|
| `[자료 확정]` | 신규 자료와 실측 결과가 일치하는 사실 | 즉시 구현·검증한다 |
| `[팀 잠정]` | 개발 중단을 피하기 위해 정한 가역적 정책 | 함수·설정·어댑터로 분리한다 |
| `[멘토 확인]` | 자료 간 충돌 또는 공식 기준이 없는 정책 | 확정 사실처럼 표현하지 않고 답변 후 교체한다 |

본 작업본과 기존 v1.9가 충돌하면 신규 데이터·평가·알람·조치·bootstrap 범위에서는 본
작업본을 우선한다. 안전·보안·Git·계층 분리처럼 신규 자료와 무관한 기존 원칙은 유지한다.

## 2. 개요

### 2.1 목적과 문서 경계

본 문서는 시스템이 제공해야 할 기능, 업무 규칙, 사용자 관점 동작, 비기능 요구사항과
수용 기준을 정의한다. DB 물리 설계, API DTO, LangGraph 노드, 트랜잭션·잠금, 인덱스 및
컴포넌트 구조는 시스템설계서 v2.0에서 정의한다. 설계 과정에서 기능이나 수용 기준 변경이
필요하면 설계서에서 임의로 바꾸지 않고 본 문서를 먼저 개정한다.

### 2.2 시스템 흐름

```text
[원본 관리]  kosa_0813.zip 해시 검증 → 원본 불변 보관 → corrected copy 생성
[감지]       Trace → Summary 재계산 → evaluation → TRACE OOS / SUMMARY OOC 알람
[보조 모델]  Summary feature → 비지도 anomaly_score → versioned IncidentModelSignal
[근거 수집]  AlarmRef → incident 집계 → PostgreSQL·Neo4j·RAG·계측 조회
[에이전트]   LangGraph → predicted fault hypothesis·원인·근거 생성
[조치]       규칙 함수 → 기본 조치 결정 → 검증된 score는 SUMMARY-only를 WARNING으로만 제한 상향
[자동 전송]  WARNING 생성 → n8n 이메일 → 완료·감사로그
[승인·전송]  EQP_HOLD 생성 → n8n 승인요청 이메일 즉시 → HITL → 승인 후 MES Mock → 감사로그
[활용]       React 5개 기능 영역(기존 8개 화면/route family 유지) + Text2SQL·동적 차트
[배포]       FastAPI + React + PostgreSQL(pgvector) + Neo4j + n8n
```

### 2.3 공개 정답이 없는 데이터의 해석

- `[자료 확정]` `lot_history.fault_code` 600건은 모두 `NRM`이며 Fault Mode 공개 정답으로
  사용하지 않는다. DDL 주석보다 멘토의 신규 데이터 설명과 실제 값의 의미를 우선한다.
- `metrology.alarm_result`의 PASS/FAIL은 제품 계측 결과이며 FOC·RFM·MFD·TMD 정답이 아니다.
- `summary_data`, `evaluation`, 두 알람 테이블은 Trace 계산 구현을 비교할 reference output이다.
  현실의 Fault를 맞힌 모델 성능 Gold로 해석하지 않는다.
- 제공 `action_history` 48건은 UI·연동 참고용 Mock이다. Agent 조치 정답이나 runtime seed로
  사용하지 않는다.
- Generator의 주입 위치·내장 Fault 매핑·HTML Mock은 운영 모델 feature·threshold 선정과 Agent
  입력에서 제외한다. 별도 seed로 생성한 합성 label은 격리된 모델 benchmark의 evaluation-only
  Gold로만 사용할 수 있으며 생산 데이터의 Fault GT나 실제 공정 성능으로 해석하지 않는다.
- 별도 전문가 라벨셋이 확정되기 전에는 Fault Accuracy·Precision·Recall·F1을 계산하거나
  프로젝트 성능으로 주장하지 않는다.

## 3. 용어 및 데이터 기준

### 3.1 주요 용어

| 용어 | 정의 |
|---|---|
| Parameter | 챔버에서 측정하는 값의 종류. 기존 `sensor` 용어를 대체한다 |
| Alarm Type | `OOS`(규격한계 이탈), `OOC`(관리한계 이탈), `IN`(정상) |
| TRACE 알람 | raw 점이 USL/LSL을 이탈한 점 단위 OOS 알람 |
| SUMMARY 알람 | Summary mean이 정상 표본 기반 UCL/LCL을 이탈한 OOC 알람 |
| `AlarmRef` | `{source, alarm_id}`. `source ∈ {TRACE, SUMMARY, R03}`이며 서로 다른 알람 소스를 충돌 없이 식별하는 공통 키. TRACE·SUMMARY는 저장 알람, R03는 `[팀 잠정]` 규칙에서 도출한 파생 사건이다 |
| Incident | `[팀 잠정]` 실제 알람이 하나 이상 존재하는 `(lot_id, chamber_id)` 조치 단위 |
| R03_CONSEC | 같은 챔버·파라미터·Recipe Step에서 연속 3 WAFER OOS가 된 사건 |
| Predicted Fault | Agent가 근거와 함께 생성한 FOC·RFM·MFD·TMD·OTH 원인 가설. 정답 라벨이 아님 |
| AnomalySignal | WAFER별 score와 model·score method 및 nullable 표시/조치 threshold·threshold version·검증 상태를 하나로 묶은 provenance DTO |
| IncidentModelSignal | incident 구성 `lot_hist_id`의 모델 점수를 집계한 versioned 입력. 검증 gate를 통과한 경우 SUMMARY OOC-only 기본 조치를 한 단계만 상향할 수 있음 |
| HITL | EQP_HOLD를 사람이 승인·반려하는 Human-in-the-loop 흐름 |
| Fault GT | 전문가가 독립적으로 검증한 Fault 정답. 현재 신규 자료에는 공개 GT가 없음 |
| Synthetic Model Gold | 운영 입력과 분리된 Generator 시나리오의 이상 주입 정답. 모델 benchmark 전용이며 생산 Fault GT·실제 조치 Gold가 아님 |

DB·API·화면에서는 `sensor`, `judgement`, `SPC` 대신 `parameter`, `alarm_type`,
`파라미터 추이`를 표준 용어로 사용한다. 기존 코드 호환 명칭은 adapter 내부에서만 허용한다.

### 3.2 신규 9개 base table 기준

| 테이블 | 기준 건수 | 용도와 주의사항 |
|---|---:|---|
| `dim_parameter` | 8행 overlay | raw Trace·evaluation용 고정 5선과 parameter metadata의 단일 출처. Summary OOC의 동적 CL·UCL·LCL은 별도 계산. 원본 seed 누락으로 corrected copy에서 생성 |
| `lot_history` | 600 | 12 LOT × 25 WAFER × 2 Process Step. `fault_code`는 평가 제외 |
| `fdc_trace` | 14,400 | 원시 시계열. `seq_no` 보정 후 적재 |
| `summary_data` | 4,800 | Trace 통계 reference output |
| `evaluation` | 4,800 | IN 4,542 / OOC 216 / OOS 42 |
| `trace_alarm_history` | 126 | raw 규격 이탈 reference output |
| `summary_alarm_history` | 47 | 관리 이탈 reference output. 시각 보정 필요 |
| `metrology` | 48 | PASS 39 / FAIL 9. Fault GT가 아님 |
| `action_history` | 48 | UI·연동 Mock. runtime 초기 데이터에서 제외 |

추가 기준은 AREA 2개(`photo`, `etch`), 설비 6대, 챔버 12개, LOT 12개,
Neo4j 38 nodes·81 relationships이다. 이 수치는 데이터 epoch 검증 기준이며 Fault·조치 정답
건수가 아니다.

## 4. 시스템 범위

### 4.1 범위 내

| 영역 | 범위 |
|---|---|
| Detection | Trace 요약·evaluation·두 알람 트랙 재현, R03, 비지도 anomaly score |
| Knowledge | Neo4j 기준정보·공정 관계, 수정된 장비 문서 RAG, 근거 ID 반환 |
| Agent | LangGraph Level 1·2, 원인 가설, 3단계 규칙 조치, HITL, 감사로그 |
| Automation | n8n SMTP 이메일 실제 연동, 승인 후 MES Mock 어댑터, channel별 멱등성 |
| Analytics | 읽기 전용 Text2SQL, 표·통계·차트, 신규 데이터용 평가 질문셋 |
| UI | 신규 자료의 5개 기능 영역을 기존 React 8개 화면/route family에 매핑해 실제 API 연동 |
| Data | 신규 ZIP 검증, 원본 불변 보관, corrected copy, 공용 DB bootstrap |
| Integration | 단일 FastAPI·React 모노레포와 Docker Compose 통합 실행 |

### 4.2 범위 외

실시간 스트리밍, 실제 생산 MES·장비 제어, PLC·SCADA, 사용자 인증·RBAC, 다단계 결재,
클라우드·Kubernetes, 실시간 WebSocket, 공개 GT가 없는 Fault 성능 주장, Generator 주입 위치를
운영 feature·threshold·Agent 입력 또는 생산 Fault GT로 사용한 평가, 새로운 Fault 자동 발견,
모델 앙상블은 범위 밖이다. Generator의 별도 seed·분리 Gold를 사용하는 합성 모델 benchmark는
생산 성능과 구분하는 조건으로 범위에 포함한다.

### 4.3 전제

- 개인 로컬 DB를 별도로 구성하지 않고 학원 제공 공용 PostgreSQL·Neo4j·n8n 서버를 사용한다.
- 같은 공용 PostgreSQL 서버 안에서 운영 runtime `kosa_agent`, 격리 Agent E2E
  `kosa_agent_e2e`, Text2SQL immutable reference·평가 `kosa_text2sql`의 논리 DB 3개를
  분리한다. 세 DB 모두 같은 corrected source manifest에서 생성하며 개인 로컬 DB로 대체하지 않는다.
- 공용 DB 초기화·migration·전체 재적재 전에는 팀에 대상 host·database·시간을 공유하고,
  대상 검증 guard를 통과해야 한다.
- 신규 DB 전환 검증이 끝날 때까지 기존 구 데이터 DB를 덮어쓰지 않는다.

## 5. 기능 요구사항

> ID는 기존 추적성을 유지한다. 우선순위는 필수·권장·도전으로 구분한다. 각 수용 기준은
> Fault GT 없이도 관찰·검증 가능한 결과로 작성한다.

### 5.1 A — Detection·Dashboard

|---|---|---|---|---|
| FR-A-01 | Summary 재계산 | `fdc_trace`를 `(lot_hist_id, parameter_id, recipe_step_no)`로 집계해 mean·표본 std(ddof=1)·min·max·count를 계산한다 | 필수 | corrected Trace에서 4,800건 생성 / 제공 `summary_data`와 키·count 완전 일치 / 숫자 절대오차 0.001 이하 |

### 7.3 공용 DB 안전

- 애플리케이션·Text2SQL·로그·migration 계정을 최소 권한으로 분리한다.
- `runtime` bootstrap profile은 `kosa_agent`와 `kosa_agent_e2e`에 적용한다. 두 DB 모두 corrected
  입력 base data를 사용하며 bootstrap 시 `action_history=0` 및 Agent·approval·delivery·audit·
  checkpoint 실행 데이터 0건을 기대한다. 운영 `kosa_agent`는 실행 후 mutable하고,
  `kosa_agent_e2e`만 승인된 reset 절차로 초기상태를 반복 복원한다.
- `evaluation` bootstrap profile은 `kosa_text2sql`에 적용하며 신규 Text2SQL·화면 질의 평가를 위해
  제공 `action_history` 48건을 profile manifest의 `fixture_type=MOCK` table metadata로 포함한다.
  이는 DB 컬럼이 아니다. 추가 curated fixture가 필요하면
  원본·corrected 파일에 섞지 않고 fixture version·hash·행 수를 profile manifest에 별도 기록한다.
  이 Mock·curated fixture는 Agent 조치 또는 Fault 정답으로 사용할 수 없다.
- verifier는 단일 공통 DB hash를 비교하지 않고 선택한 profile의 table별 포함 여부·컬럼·행 수·
  content hash·fixture metadata를 기대 상태와 비교한다.
- profile manifest의 immutable content hash 대상은 base/reference table과 명시적으로 versioning한
  fixture로 한정한다. runtime의 action·Agent·approval·delivery·audit·checkpoint 실행 테이블과
  실행마다 누적되는 runtime/evaluation `nl_query_log`는 immutable base content hash에 섞지 않는다.
- verifier는 **bootstrap 초기상태 모드**와 **운영 중 검증 모드**를 구분한다. 초기상태 모드는
  profile별 base/reference hash와 runtime action·실행 테이블 0건, evaluation Mock 48건을 확인한다.
  운영 중 모드는 mutable table의 초기 행 수·content hash 일치를 요구하지 않고 schema·제약·권한과
  해당 실행의 versioned artifact·감사 추적을 검증한다. evaluation `nl_query_log` 누적은 reference
  data 변조로 판정하지 않는다.
- destructive bootstrap과 E2E reset은 허용된 공용 테스트 대상에서만 실행하며 host·database
  allowlist와 명시적 확인 옵션을 강제한다.
- 공용 Neo4j에는 raw `master.cypher`의 `MATCH (n) DETACH DELETE n`을 직접 실행하지 않는다.
  기본 적재 대상은 empty/fresh graph로 제한한다. 이미 데이터가 있는 graph의 교체는 기존 graph
  fingerprint 확인, 팀 공유, 복구 가능한 백업, 대상 명시 확인을 모두 갖추지 않으면 거부한다.
- Agent E2E는 `kosa_agent_e2e`의 입력 base data를 유지하고 action·Agent·approval·delivery·audit·
  checkpoint 실행 데이터만 초기화한다. 운영 `kosa_agent`와 immutable `kosa_text2sql`은 E2E reset
  대상으로 허용하지 않는다.
- 공용 컨테이너를 장애 주입 목적으로 중지하지 않는다. dependency override·테스트 webhook을 사용한다.

### 8.1 두 알람 트랙

1. raw 값이 USL/LSL을 넘으면 점 단위 TRACE OOS를 생성한다. `upper_only=true` parameter는

2. Summary는 판정을 포함하지 않는 통계다.
3. evaluation은 각 Summary Window의 raw point OOS·OOC 수와 대표 alarm type을 기록한다.
4. SUMMARY OOC는 같은 `(chamber, parameter, recipe_step_no)`의 비OOS Summary mean으로
   CL·UCL·LCL을 계산하여 mean 이탈을 판정한다.
5. 두 알람의 ID 공간이 겹칠 수 있으므로 조회·실행·로그에서는 항상 `AlarmRef`를 사용한다.
6. 공개 `GET /alarms`는 필수 `date_from`·`date_to`·`area`를 적용한 뒤 `source`와
   `include_derived`를 생략하면 저장된 TRACE·SUMMARY만 반환한다. corrected 전체 기간
   `2026-08-01~2026-08-12`와 `area=ALL`을 명시한 경우에만 그 저장 알람 합계가 173건이다.
   R03는 `source=R03` 또는 `include_derived=true`로 명시한 경우에만 파생 사건 3건을 노출한다.
   Agent incident 근거는 공개 목록의 조회 필터와 무관하게 관련 R03 `AlarmRef`를 포함한다.

### 8.2 R03_CONSEC `[팀 잠정]`

```text
key       (chamber_id, parameter_id, recipe_step_no)
order     chamber_wafer_cum ASC, track_in_at ASC, lot_hist_id ASC
boundary  LOT 경계에서 초기화하지 않음
reset     비OOS에서 연속 수 0
emit      run == 3이 되는 시점에 한 번만 생성; 4 이상에서 중복 없음
owner     세 번째 OOS가 속한 lot·chamber incident
```

신규 자료의 단순 `OOS 3+`와 연속 3 WAFER R03의 동일성은 확정되지 않았다. 본 작업본은
연속성을 EQP_HOLD 근거로 사용하며 최종 귀속·매핑은 `[멘토 확인]`으로 둔다.

### 8.3 3단계 조치와 model signal 제한 상향 `[팀 잠정]`

| incident 근거 | 신뢰 가능한 `IncidentModelSignal` | action_code | 승인 | 외부 채널 |
|---|---|---|---|---|
| R03 존재 | 사용하지 않음 | `EQP_HOLD` | PENDING | 승인 요청 EMAIL 즉시, 승인 후 MES Mock |
| TRACE OOS가 있으나 R03 없음 | 사용하지 않음 | `WARNING` | AUTO | EMAIL |
| SUMMARY OOC만 존재 | `MODEL_SIGNAL_ENABLED=true`, threshold `VERIFIED`, coverage 100%, `incident_score >= action_threshold` | `WARNING` | AUTO | EMAIL |
| SUMMARY OOC만 존재 | `MODEL_SIGNAL_ENABLED=false`·미준비·불일치·coverage 미달 또는 threshold 미만 | `MONITORING` | AUTO | 없음 |

규칙 함수는 먼저 R03 → TRACE OOS → SUMMARY OOC 순서로 기본 조치를 결정한 뒤, 검증된 model
signal을 제한적으로 적용한다. 한 incident에는 가장 높은 최종 조치 한 건만 만든다.

- `IncidentModelSignal`은 incident AlarmRef를 resolve한 고유 `lot_hist_id`별 score를 중복 제거·안정
  정렬한 뒤 `threshold_validation_status=VERIFIED`이고 동일 model·score method·threshold version인
  유효 score 중 `max`로 집계한다.
- `expected_member_count == valid_member_count`일 때만 coverage 100%다. mixed version, nullable score,
  모델·threshold 미준비 또는 policy가 허용하지 않은 version은 상향에 사용할 수 없다.
- 환경변수 `MODEL_SIGNAL_ENABLED`의 기본값은 `false`다. FR-A-04의 versioned synthetic gate를
  통과하고 팀이 승인한 model·threshold·action policy 조합에서만 `true`로 전환한다.
  승인 artifact가 없거나 현재 version 조합과 일치하지 않으면 환경변수가 `true`여도 정책 검증에서
  signal을 적용하지 않고 기본 조치로 fallback한다.
- score는 SUMMARY OOC라는 독립 규칙 근거가 있을 때 `MONITORING → WARNING` 한 단계 상향만
  허용한다. 조치 하향, 알람 없는 incident·action 생성, `WARNING → EQP_HOLD`, `EQP_HOLD`·HITL
  생성에는 사용할 수 없다.
- predicted fault·LLM 설명·metrology PASS/FAIL은 조치 등급과 승인 필요 여부를 변경하지 못한다.
- action 근거에는 `base_action`, `final_action`, `score_effect`, incident/member score, threshold,
  max score member, coverage, model·score method·threshold·policy version을 snapshot한다.
- 신규 corrected data의 model signal OFF baseline은 incident 10개,
  `MONITORING 5 / WARNING 2 / EQP_HOLD 3`이다. ON 결과는 동결된 model·threshold·policy별 fixture로
  새로 기록하며 두 결과 모두 실제 조치 Gold가 아니다.

### 8.4 승인·전송 상태

```text
MONITORING  AUTO      → 외부 호출 없음 → COMPLETED
WARNING     AUTO      → EMAIL WAITING→SENDING→SENT|FAILED
EQP_HOLD    PENDING   → 승인요청 EMAIL 전송
             ├ APPROVED → MES WAITING→SENDING→SENT|FAILED
             └ REJECTED → MES CANCELED, 미전송
```

- 조치가 결정되면 전송·승인 전 `action_history`를 먼저 생성한다.
- EMAIL과 MES 상태·시도·시각·payload hash는 `(action_id, channel)`별로 관리한다.
- provider 응답 유실 또는 stale `SENDING`은 `UNKNOWN`으로 전이하고 자동 재발송하지 않는다. 운영자가 provider message ID 등을 대조해 `SENT`·`FAILED`로 해소한 뒤에만 후속 처리한다.
- 승인·반려는 기존 action을 갱신하며 새 action을 만들지 않는다.
- `audit_log`는 append-only로 사용한다.
