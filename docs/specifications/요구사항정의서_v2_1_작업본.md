### 1.1 개정 목적

제공된 최종 패키지는 이전 `kosa_0813.zip` 기준과 달리 복구된 합성 Fault
라벨, 12건의 incident·조치 reference, 보정된 Trace 순번과 시간값, 44 nodes·85
relationships 그래프를 포함한다. 본 버전은 물리 CSV·Generator 실측값을
단일 기준으로 고정하고 이전 v2.0의 다음 전제를 폐기한다.

- `fault_code` 600건이 모두 `NRM`이라는 전제
- 공개 Fault 정답이 없어 분류 평가를 할 수 없다는 전제
- anomaly score로 `MONITORING`을 `WARNING`으로 상향하는 조치 규칙
- incident 10건·action 10건, 저장 알람 173건, Neo4j 38/81 기준

## 2. 개요

### 2.1 목적과 문서 경계

본 문서는 사용자 기능, 업무 규칙, 평가 방법, 비기능 요구사항과 수용 기준을
정의한다. DB 물리 설계, API DTO, LangGraph State·Node, 트랜잭션, 인덱스와
배포 절차는 시스템설계서 v2.1에서 정의한다. 기능이나 수용 기준을 바꾸려면
설계서나 WBS를 먼저 수정하지 않고 본 문서를 먼저 개정한다.

### 2.2 시스템 흐름

```text
[원본 관리]   최종 ZIP SHA-256 검증 → 원본 불변 보관 → dataset epoch 등록
[데이터]    9개 CSV·DDL 검증 → 용도별 DB bootstrap → row/hash/readiness 검증
[감지]        Trace → Summary 재계산 → evaluation → TRACE OOS / SUMMARY OOC / R03
[모델]        Summary feature → 비지도 anomaly score → 버전된 참고 근거
[근거 수집]   AlarmRef → incident 집계 → PostgreSQL·Neo4j·RAG·계측 조회
[에이전트]   LangGraph → predicted fault·원인·근거·조치 설명
[조치]        규칙 함수 → MONITORING / WARNING / EQP_HOLD
[자동화]      WARNING·승인요청 n8n SMTP, 승인 후 Kafka MES Mock, 감사로그
[활용]        React 7화면(Dashboard·Alarms·Agent·Documents·Ontology·Analytics·Audit) + 호환 하위 route
[배포]        FastAPI + React + PostgreSQL(pgvector) + Neo4j + Kafka + n8n
```

### 2.3 합성 정답과 운영 정답의 구분

- `[패키지 확정]` 최종 데이터의 `fault_code`는 Generator가 생성한 공개 합성
  Fault 라벨이다.
- 평가 artifact에 `public_fault_ground_truth_available=true`,
  `label_source=SYNTHETIC_GENERATOR`, `production_ground_truth_available=false`,
  `usage_scope=EVALUATION_ONLY`를 함께 기록한다.
- Fault 라벨은 모델·Agent의 입력 feature, 프롬프트, Tool 반환, 임계값 선정,
  조치 결정에 사용하지 않는다.
- 라벨을 차단한 추론을 완료한 뒤 격리된 평가기에서만 예측과 비교한다.
- 합성 데이터의 정확도·Precision·Recall·F1은 `합성 benchmark`로만 표현하고,
  실제 생산 공정의 성능으로 해석하지 않는다.
- Agent 5-class 평가는 12 incident 중 단일 non-NRM 합성 라벨을 가진 7개 incident에만
  적용한다. SUMMARY-only 5개 incident는 모두 NRM이므로 5-class 분모에서 제외하고
  `NO_INJECTED_FAULT` 그룹으로 별도 보고한다.
- `metrology`는 600개 `lot_history` 중 48개 표본만 포함한다. PASS 39·FAIL 9에 대한
  Detection 지표는 이 관측 표본에만 유효하며 600건 전체나 생산 공정으로 외삽하지 않는다.
- 실제 생산 데이터에 대해서는 전문가 검수 라벨이 없으므로
  `production_ground_truth_available=false`를 유지한다.

## 3. 용어 및 최종 데이터 기준

### 3.1 주요 용어

| 용어 | 정의 |
|---|---|
| Parameter | 챔버에서 측정하는 값의 종류. DB·API의 표준 용어 |
| Alarm Type | `OOS`규격한계 이탈, `OOC`관리한계 이탈, `IN`정상 |
| TRACE 알람 | raw point가 USL/LSL을 이탈한 점 단위 OOS 알람 |
| SUMMARY 알람 | Summary mean이 UCL/LCL을 이탈한 OOC 알람 |
| `AlarmRef` | `{source, alarm_id}`. `source ∈ {TRACE, SUMMARY, R03}`인 공통 알람 식별자 |
| Incident | 알람이 하나 이상 존재하는 `(lot_id, chamber_id)` 조치 단위 |
| R03_CONSEC | 같은 챔버·파라미터·Recipe Step에서 연속 3 WAFER OOS가 된 파생 사건 |
| Predicted Fault | Agent가 근거로 생성한 `FOC\|RFM\|MFD\|TMD\|OTH` 원인 가설 |
| Public Synthetic Fault GT | 최종 Generator가 `lot_history.fault_code`에 기록한 평가용 합성 라벨 |
| Anomaly Evidence | WAFER별 score와 model·feature·normalization·version provenance를 포함한 Agent 참고 근거 |
| HITL | `EQP_HOLD`를 사람이 승인·반려하는 Human-in-the-loop 흐름 |

### 3.2 최종 9개 CSV 기준

| 테이블 | 기준 건수 | 용도와 주의사항 |
|---|---:|---|
| `dim_parameter` | 8 | 고정 5선과 parameter metadata. 임시 보정 layer가 아닌 최종 seed |
| `lot_history` | 600 | 12 LOT × 25 WAFER × 2 Process Step. 합성 Fault 라벨 포함 |
| `fdc_trace` | 14,400 | `seq_no=0~5`가 Recipe Step을 넘어 전역 순번으로 유일하게 저장됨 |
| `summary_data` | 4,800 | Trace 통계 reference output |
| `evaluation` | 4,800 | `IN 4,538 / OOC 216 / OOS 46` |
| `trace_alarm_history` | 138 | raw 규격한계 이탈 reference output |
| `summary_alarm_history` | 51 | 동적 관리한계 이탈 reference output |
| `metrology` | 48 | `PASS 39 / FAIL 9`. Fault Mode 라벨은 아님 |

- incident: 12건
- 조치 reference: `MONITORING 5 / WARNING 4 / EQP_HOLD 3 = 12`
- Neo4j: `44 nodes / 85 relationships`
- AREA 2개, 설비 6대, 챔버 12개, LOT 12개, parameter 8개

## 4. 시스템 범위

### 4.1 범위 내

| 영역 | 범위 |
|---|---|
| Detection | Trace 요약·evaluation·TRACE/SUMMARY 알람·R03 재현, 비지도 anomaly score |
| Knowledge | Neo4j 기준정보·공정 관계, 검증된 문서 RAG, 근거 ID |
| Agent | LangGraph Level 1·2, Fault 가설·근거·조치 설명, 3단계 규칙 조치, HITL |
| Automation | n8n SMTP 이메일, Kafka MES Mock, 채널별 멱등성·write-back |
| Analytics | 읽기 전용 Text2SQL·질의 이력·immutable 평가 이력과 전역 감사 조회를 팀 release 필수로 제공 |
| UI | Dashboard·Alarm History·Agent·Documents·Ontology·자연어 분석·감사로그 7개 화면을 실제 API와 연동 |
| Data | 최종 ZIP 검증, epoch·manifest, 용도별 공용 DB bootstrap |
| Integration | FastAPI·React·외부 공용 PostgreSQL·Neo4j·n8n, 팀 Kafka·MES Mock 통합 |

### 4.2 범위 외

실제 생산 MES·장비 제어, PLC·SCADA, 다단계 결재, 실시간 WebSocket, 클라우드·
Kubernetes, 생산 Fault GT가 있는 것처럼 표현한 성능 주장, 합성 라벨·Generator
주입 정보를 운영 feature·Agent 근거·조치에 사용하는 기능은 범위 밖이다.

### 4.3 공용 환경 전제

- 학원 제공 공용 PostgreSQL·Neo4j·n8n 서버를 사용한다.
- 동일 PostgreSQL 서버에서 runtime `kosa_agent`와 Agent E2E `kosa_agent_e2e`를
  논리적으로 분리한다.
- `kosa_text2sql`은 이름과 무관하게 최종 reference·공개 합성 라벨의 격리 평가 DB로 필수
  유지한다. Text2SQL 평가 실행은 이 DB의 별도 readonly projection만 사용하며 runtime DB로
  fallback하지 않는다.
- 활성화된 DB는 모두 동일한 최종 epoch과 용도별 profile manifest를 사용한다.
- DB·Neo4j 초기화·교체·migration 전에 대상 host·database·fingerprint를 확인하고
  팀에 작업 시간과 영향을 공유한다.
- `master.cypher`는 전체 노드 삭제 문을 포함하므로 원본을 공용 Neo4j에
  직접 실행하지 않고 destructive-safe loader를 사용한다.
- PostgreSQL·Neo4j·n8n은 이미 운영되는 **외부 canonical 공용 서비스**다. 팀
  `docker compose`는 Backend·Frontend·Kafka·MES Mock만 기동하며 두 번째 PostgreSQL·
  Neo4j·n8n 인스턴스를 만들지 않는다.

| FR-A-09 | 모델 고도화 | 라벨 없이 train·validation의 재현성·score 분포로 후보를 고정한 뒤 격리 synthetic holdout을 1회 평가한다 | 도전 | holdout 결과를 같은 후보·threshold 선택에 재사용하지 않고 합성·운영 성능 표현 분리 |

`GET /alarms`는 최종 물리 React의 무파라미터 호출과 호환되어야 한다.

- `date_from`·`date_to`·`area`는 선택 파라미터다.
- 날짜를 생략하면 final epoch 전체 기간, `area`를 생략하면 `ALL`로 처리한다.
- 날짜는 두 값을 함께 주거나 함께 생략해야 하며 한쪽만 제공하면 422를 반환한다.
- 무파라미터 기본 응답은 파생 R03를 제외한 저장 알람 189건이다.
- `source=R03`는 3건, `include_derived=true`는 저장 알람과 R03를 합한 192건을 반환한다.
- 유효한 필터의 결과가 없으면 200과 빈 목록·0 집계를 반환하고 bootstrap source 자체가
  없으면 Empty가 아니라 readiness 실패로 처리한다.

## 6. Tool 공통 요구사항

Tool 5종과 입력 signature는 다음으로 고정한다.

```text
get_fdc_summary(lot_hist_id)
get_equipment_context(chamber_id)
search_documents(query, model_code=None, top_k=4)
send_action(action_id)
generate_analysis_plan(question)
```

1. 모든 Tool 결과는 `ok`, `reason`, 도구별 domain payload만 포함한다. 성공 시
   `reason=""`, 실패 시 domain payload는 null 또는 빈 목록이다.
2. 실패 `reason` 접두어 allowlist는 `NOT_FOUND:`, `TIMEOUT:`, `MODEL_NOT_READY:`,
   `LLM_NOT_READY:`, `GRAPH_SHAPE_ERROR:`, `DEPENDENCY_ERROR:`, `POLICY_REJECTED:`,
   `IDEMPOTENCY_CONFLICT:` 여덟 종뿐이다. `GRAPH_SHAPE_ERROR:`는 graph에 **연결은
   됐으나 반환 형상이 계약과 다른** 경우이고 `DEPENDENCY_ERROR:`는 조회 자체가
   실패한 경우다. 둘을 합치면 "근거를 못 얻었다"와 "근거가 계약을 어겼다"를
   구분할 수 없어 원인 분류가 약해진다.
3. `latency_ms`·`SUCCESS|ERROR|TIMEOUT`은 Tool 반환값이 아니다. 공통 wrapper가 호출당
   `agent_tool_call` 한 행에 입력·출력과 함께 정확히 한 번 기록한다. 독립 Analytics로만 실행한
   `generate_analysis_plan`은 선택 D 경로에서만 evaluation DB의 `nl_query_log`에 기록하고
   Agent에서 호출한 경우에만 같은 wrapper를 사용한다.
4. ID·Enum·공유 payload는 `backend/app/common` 계약을 재사용하고 도메인별로
   재정의하지 않는다.
5. timeout·연결 오류·검색 0건도 contract 테스트한다.
6. 읽기 Tool의 caller 대기 timeout은 8초 이하로 관리한다. `send_action` wrapper deadline은
   n8n webhook timeout보다 5초 길게 파생해 adapter가 끝나기 전에 wrapper가 먼저 종료되지
   않게 한다(기본 `N8N_WEBHOOK_TIMEOUT_SEC=30`이면 35초).
7. `send_action(action_id)`은 저장된 action·approval·delivery plan을 조회해 EMAIL과 MES를
   구분한 채널별 결과와 이번 실행의 `effect_attempted`·실제 `effect_channel`을 반환하며
   호출자가 channel이나 agent_run_id를 다시 주입하지 않는다.
8. Fault GT는 Tool 입력·출력·예외 상세·Agent State에 포함하지 않는다.
9. anomaly score는 근거와 provenance로만 반환하며 action code·severity·approval 필요
   여부를 파생하는 필드로 사용하지 않는다.

## 7. 데이터·공용 DB 요구사항

### 7.1 원본·epoch 보존

- 원본 ZIP은 수정하지 않고 SHA-256와 수집 시각을 기록한다.
- ZIP 전체를 저장소에 풀지 않고 필요한 CSV·DDL·Generator·Cypher·RAG 소스만
  선별해 provenance와 함께 관리한다.
- `node_modules`, `__pycache__`, 참고 backend/frontend, 로컬 compose 비밀번호는 승계하지
  않는다.
- source file manifest에 상대경로·크기·SHA-256를 기록한다.
- dataset epoch에 ZIP hash·manifest hash·schema version·graph revision을 연결한다.
  RAG 적재는 별도 버전 교체 lifecycle 없이 source·corrected hash와 문서·chunk 수·차원·검색
  smoke 결과로 검증한다.

### 7.2 원본 검증

이전 자료에 필요했던 `dim_parameter` 생성, `seq_no` 보정, Summary·Metrology
시각 생성은 최종 패키지에 이미 반영되었으므로 더 이상 correction 단계로
수행하지 않는다. 대신 다음을 검증한다.

1. 9개 CSV의 헤더·유일 키·FK·행 수를 검증한다.
2. Trace `seq_no=0~5`와 PK `(lot_hist_id, parameter_id, seq_no)` 중복 0건을 검증한다.
3. Trace에서 Summary·evaluation·TRACE/SUMMARY alarm을 재계산해 CSV와 비교한다.
4. Fault·evaluation·action 분포와 12 incident 대응을 검증한다.
5. Generator를 임시 경로에서 실행해 9개 CSV와 byte-identical임을 검증한다.
6. DDL은 fresh schema 전용으로 다루고 기존 공용 DB에 직접 실행하지 않는다.

### 7.3 profile과 저장 정책

| profile | base 정보 | mutable runtime |
|---|---|---|
| `kosa_agent` | 9개 base schema를 만들고 `action_history`를 제외한 8개 CSV만 적재. `action_history` table은 0행 | Agent run·action·approval·delivery·audit |
| `kosa_agent_e2e` | runtime과 같은 9개 schema·8개 CSV·action 0 상태를 안전하게 초기화 | 격리 E2E 상태 |
| `kosa_text2sql` | 최종 9개 CSV 전부와 `action_history` reference 12건을 포함한 격리 evaluation/reference DB | 읽기 전용 평가 실행. 운영 질의 로그를 기록하지 않음 |

runtime의 규칙 12건은 빈 action 상태에서 실제 규칙 함수로 재생성해 reference
분포와 비교한다. 제공 `action_history` 12건을 runtime action으로 복사하지 않는다.

### 7.4 공용 DB 안전

1. destructive operation은 명시적 `--confirm`과 정확한 host·database 확인을 요구한다.
2. DB 이름만으로 안전을 판단하지 않고 host·port·database·fingerprint를 검사한다.
3. 공용 데이터를 바꾸기 전에 복구 가능한 백업과 영향 범위를 확인한다.
4. Text2SQL 실행 계정은 DB 레벨 `READ ONLY`이고
   log writer는 업무 테이블 조회·실행 권한을 가지지 않는다.
5. manifest에 계정·비밀번호·DSN·host를 기록하지 않는다.

## 8. 판정·조치·상태 규칙

### 8.1 알람 판정

1. Summary는 `(lot_hist_id, parameter_id, recipe_step_no)`별 Trace 통계로 계산한다.
2. TRACE OOS는 raw point가 `spec_upper` 초과 또는 `spec_lower` 미만일 때 생성한다.
3. evaluation은 raw point OOS·OOC 수와 대표 alarm type을 기록한다.
4. SUMMARY OOC는 같은 `(chamber, parameter, recipe_step_no)`의 비OOS Summary mean으로
   CL·UCL·LCL을 계산한 뒤 mean 이탈을 판정한다.
5. 알람은 source별 ID 공간이 다르므로 항상 `AlarmRef`로 조회·실행·기록한다.
6. 기본 목록은 저장된 TRACE·SUMMARY 189건을 반환하고 R03는 `source=R03`
   또는 `include_derived=true`를 명시한 경우에만 포함한다.

### 8.2 R03_CONSEC

```text
key       (chamber_id, parameter_id, recipe_step_no)
order     chamber_wafer_cum ASC, track_in_at ASC, lot_hist_id ASC
boundary  LOT 경계에서 초기화하지 않음
reset     비OOS에서 연속 수 0
emit      run == 3이 되는 시점에 1회만 생성, run > 3에서 중복 없음
owner     세 번째 OOS가 속한 lot·chamber incident
```

R03 ID는 `source`, `lot_hist_id`, `chamber_id`, `parameter_id`, `recipe_step_no`, `policy_version`의 canonical
JSON SHA-256로 계산한 `R03-<앞 20개 lowercase hex>`로 고정한다. `policy_version`은
`R03_CONSEC_V1`로 고정하고 JSON은 UTF-8·정렬 key·공백 없는 separator·정수형 step을 사용한다.
해시 payload에는 `source="R03"`, owner `lot_hist_id`, `chamber_id`, `parameter_id`, `recipe_step_no`,
`policy_version`만 넣고 display 시각이나 member 배열 순서는 넣지 않는다.

R03 상세 근거는 서로 다른 두 목록으로 보존한다.

- `member_wafer_refs`: 연속 OOS를 구성한 `{lot_hist_id, wafer_id}` 정확히 3개
- `member_alarm_refs`: 위 세 WAFER의 해당 parameter·step raw OOS point를 가리키는 TRACE
  AlarmRef 전체. 최종 epoch에서는 R03 한 건당 9개

WAFER 목록은 R03 계산 순서, AlarmRef 목록은 그 WAFER 순서 안에서 `seq_no ASC, alarm_id ASC`로
직렬화한다.

Generator의 incident 집합은 참고 재현물이며 R03 persisted fixture가 아니다. 팀의 `run == 3`
정책과 위 serialization으로 R03를 재생성해 3건·owner·member를 별도 회귀 검증한다.

### 8.3 3단계 조치

| incident 근거 | action_code | 승인 | 외부 채널 |
|---|---|---|---|
| R03 존재 | `EQP_HOLD` | `PENDING` | n8n 승인요청 EMAIL, 승인 후 Kafka MES Mock |
| TRACE OOS가 있으나 R03 없음 | `WARNING` | `AUTO` | n8n EMAIL |
| SUMMARY OOC만 존재 | `MONITORING` | `AUTO` | 없음 |

조치 우선순위는 `R03 > TRACE > SUMMARY`이며 incident당 가장 높은 조치 1건만 만든다.

- anomaly score는 Agent가 이상 정도를 설명하는 참고 근거다.
- score는 incident 생성, action code, severity, 승인 필요 여부, 전송 채널을
  상향·하향·추가하지 못한다.
- predicted fault, LLM 설명, metrology PASS/FAIL도 조치를 변경하지 못한다.
- 조치 근거에는 적용한 policy version과 사용한 AlarmRef snapshot을 기록한다.
- 최종 데이터에서 incident 12건은 `MONITORING 5 / WARNING 4 / EQP_HOLD 3`으로
  재현되어야 한다.

### 8.4 승인·전송 상태

```text
MONITORING  AUTO      → 외부 호출 없음 → COMPLETED
WARNING     AUTO      → EMAIL WAITING→SENDING→SENT|FAILED|UNKNOWN
EQP_HOLD    PENDING   → 승인요청 EMAIL
             ├ APPROVED → MES WAITING→SENDING→SENT|FAILED|UNKNOWN
             └ REJECTED → MES CANCELED, 미전송
```

- action은 승인·전송보다 먼저 생성한다.
- EMAIL과 MES는 `(action_id, channel)`별 독립 delivery 상태·시도·payload hash를 가진다.
- 응답 유실·stale `SENDING`은 `UNKNOWN`으로 전이하고 자동 재발송하지 않는다.
- 승인·반려는 기존 action을 갱신하고 새 action을 만들지 않는다.
- 감사로그는 append-only로 유지한다.
