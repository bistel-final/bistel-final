## 2. 개요

### 2.1 목적

본 문서는 「LangGraph 기반 반도체 FDC 이상감지 에이전트 및 데이터 플랫폼」이 구현해야 할 기능·비기능 요구사항을 정의한다. 각 요구사항에 식별자(ID)와 수용 기준을 부여하여 이후 산출물인 시스템 설계서(8/14) 및 테스트·평가 결과서(9/8)와의 추적성을 확보하는 것을 목적으로 한다.

### 2.2 문서 범위 및 후속 산출물과의 관계

본 요구사항 정의서는 시스템이 제공해야 하는 기능·비기능 요구사항, 업무 규칙, 사용자 관점의 동작, 상태·예외 정책 및 수용 기준을 정의한다. 아키텍처, LangGraph 내부 구성, API DTO, DB 접근 구조, 트랜잭션·동시성 구현 방식, 인덱스·잠금 및 컴포넌트 구조는 시스템 설계서에서 정의한다.

시스템 설계 과정에서 기능 범위, 업무 규칙 또는 수용 기준의 변경이 필요한 경우 설계서에서 임의로 변경하지 않고 요구사항 정의서를 먼저 개정하며, 요구사항 추적 매트릭스를 함께 갱신한다. 단, 멘토 요구 항목인 Tool 명세, 기준정보 스키마, 문서셋, 판정 규칙 및 Text2SQL 질의셋은 추적성과 평가 기준 확보를 위해 본 문서에 포함한다.

### 2.3 시스템 개요

반도체 전공정 중 PHOTO·ETCH 2개 AREA의 장비 센서 데이터(FDC trace)를 WAFER 단위로 수집·요약하여 규칙과 이상감지 모델로 이상을 감지(Detection)하고, 발생한 알람에 대해 LangGraph 에이전트가 장비 관계(Neo4j)와 장비 매뉴얼(RAG)을 근거로 이상 유형을 분류·원인 분석·조치 권고(Classification)한다. 생산 영향이 큰 EQUIPMENT HOLD는 사람 승인(HITL) 후 전송하며, 자연어 질의(Text2SQL)와 React 기반 데이터 플랫폼으로 데이터 활용을 지원하고 전 과정을 감사로그로 기록한다.

```
[감지]  trace → 요약 → 규칙+모델 → 알람          (A)
[분류]  alarm_id → incident 집계 → 에이전트(Tool 3종: 요약/관계/문서) → 유형·원인·조치   (C, 근거는 A·B)
[승인]  EQP_HOLD → interrupt → 사람 승인 → 재개                   (C + 화면)
[전송]  n8n → MES·메일 모의 전송 → 감사로그                        (C)
[활용]  Text2SQL·통계·차트 / 감사로그 조회                         (D)
[통합]  단일 FastAPI + 단일 React + Docker Compose                 (공동, 통합 관리 C)
```

### 2.4 대상 독자

멘토, 프로젝트 팀원 4인, 과정 평가자

## 3. 용어 정의

| 용어 | 정의 |
|---|---|
| FDC | Fault Detection and Classification. 이상 감지(규칙·모델)와 분류(에이전트)로 구성 |
| OOS / OOC | Out of Spec(규격한계 이탈, 이상 확정) / Out of Control(관리한계 이탈, 경고) |
| LSL·LCL·TARGET·UCL·USL | 센서별 5개 기준선. 관리한계(LCL/UCL)가 규격한계(LSL/USL) 안쪽에 위치 |
| RECIPE STEP | 공정 조건의 세부 단계(EXPOSE/DEVELOP, MAIN_ETCH/OVER_ETCH). FDC 판정 단위 |
| FAULT CODE | 이상 유형 4종: FOC(초점), RFM(RF정합), MFD(가스유량), TMD(척온도) + NRM(정상) |
| R03_CONSEC | 동일 CHAMBER·SENSOR·RECIPE STEP에서 챔버 처리 순서상 연속 3 WAFER OOS 발생 시 챔버 이상 판정. `chamber_wafer_cum ASC` 기준으로 **LOT 경계를 넘어** 계산 |
| HITL | Human-in-the-loop. EQP_HOLD를 사람 승인 후에만 전송하는 구조 |
| Text2SQL | 자연어 질문을 SQL로 변환하여 조회하는 기능. LLM은 계획 생성만, 실행은 코드 |
| 골든 시나리오 | E2E 검증 시나리오 4건(자동조치/승인/반려/실패 처리). 4인 공동 책임. 상세는 부록 B |
| IN_CONTROL | DB 판정값 3종(IN_CONTROL·OOC·OOS) 중 정상. TROUBLE 문서 원문의 "IN_SPEC"은 본 문서에서 **"모두 IN_CONTROL(= OOC/OOS 0건)"**로 통일 표기 — OOC도 규격한계 안쪽이라 IN_SPEC만으로는 해석이 갈리기 때문 |

상세 용어는 배포 패키지 「00_용어집.pdf」를 따른다.

## 4. 시스템 범위

### 4.1 범위 내 (In Scope)

| 기능 | 범위 |
|---|---|
| Detection | 규칙 3종(한계선·연속) + 이상감지 모델 1종(IsolationForest), 배치 판정 |
| Classification | 이상 유형 4종 분류 + 원인 설명 + 조치 권고 (근거: 관계·문서) |
| 문서 검색 | 기반구축에서 적재 완료된 md 문서 3종 청크·임베딩의 검증·검색 (bge-m3, pgvector) |
| 관계 조회 | Neo4j 기준정보 관계 조회 (상하류·형제 챔버) |
| 조치 | 권고 생성 + n8n 경유 모의 전송(MES·메일). EQP_HOLD는 승인 후 전송 |
| UI | React 기반 데이터 플랫폼과 FastAPI Backend를 구현한다. 기존 Streamlit 원안의 7개 화면과 핵심 도메인 범위는 유지하고 UI 및 API 구현 방식을 FastAPI+React로 변경한다 |
| 자연어 질의 | Text2SQL(읽기 전용) + 통계·차트 계획 |

### 4.3 전제 및 가정

- 데이터는 공정 물리 특성을 반영한 합성 데이터이며 배포 패키지 원본을 수정 없이 사용한다

- LLM은 KOSA 지급 API 키를 사용한다(2026.07 합의, 배포 기본값 Ollama 대체). 제공자 전환이 가능하도록 .env로 추상화하며, 실제 사용 모델명은 agent_run.llm_model에 기록한다

- 승인 대기 수는 날짜·AREA 필터와 무관한 전체 `approval_request.status='PENDING'` 건수이며 C API 또는 공유 ApprovalService 결과를 사용한다

## 6. Tool 명세 【멘토 요구 ①】

**공통 계약** — 반환: `{ok: bool, ...도구별 필드..., reason: str}` / 실패·타임아웃 시 예외를 던지지 않고 `{ok: false, reason}` 반환 (타임아웃은 `reason: "TIMEOUT: ..."`) / C의 Agent 흐름에서 호출되는 A·B·C Tool의 호출 이력·지연시간은 `agent_tool_call`에 기록 / 독립 Analytics 기능인 D의 `generate_analysis_plan` 호출은 `nl_query_log`에 기록하며, 추후 Agent에 연결하는 경우에만 `agent_tool_call`에도 기록 / 원안(개발 가이드 04) 대비 변경 시 사유 명기.

### 6.1 get_fdc_summary — 구현 A, 사용 C

```
입력: lot_hist_id: str (예: "LH-00101")
출력: {ok, wafer:{lot_id, wafer_no, chamber_id, step_id},
      sensors:[{sensor_id, sensor_name, recipe_step_name,
                value_mean, value_std, value_min, value_max,
                spec_lower, ctrl_lower, target, ctrl_upper, spec_upper,
                judgement}],
      anomaly_score: float, anomaly_threshold: float, is_anomaly: bool,
      reason}
```
- 한계선 5개 동봉 필수(LLM의 이탈 정도 판단 근거). 원안 대비 anomaly_* 필드 추가(모델 판단 근거 제공). `value_std`를 포함하며 역할분담 v9.5의 Tool 계약과 동일하다.

### 6.2 get_equipment_context — 구현 B, 사용 C

```
입력: chamber_id: str (예: "PHO-01-C1")
출력: {ok, equipment:{equipment_id, model_code, ...}, area, step,
      sibling_chambers:[...], upstream:[...], downstream:[...], reason}
```
- 상하류는 Neo4j UPSTREAM_OF 관계 기준. 연쇄 이상 판단의 핵심 근거.

### 6.3 search_documents — 구현 B, 사용 C

```
입력: query: str, model_code: str|None (예: "ET-7500"), top_k: int = 4
출력: {ok, hits:[{title, section, score, content}], reason}
```
- model_code 지정 시에도 COMMON 문서(트러블슈팅 가이드) 항상 포함. score = 1 − 코사인 거리.

### 6.4 send_action — 구현·사용 C

```
입력: action_id: str, agent_run_id: str
출력: {ok, action_id, sent: bool, reason}
```
- **원안 시그니처(lot_id, equipment_id, ... 5개 인자)를 의도적으로 변경**: 조치 내용은 action_history 행 생성 시 확정되며, Tool은 action_id로 조회해 전송만 수행 → LLM이 전송 시점에 조치 내용을 재조합하는 위험 제거 + 멱등성 확보.
- sent는 "최종 전송 상태". 이미 SENT인 건 재전송 없이 sent=true 반환. EQP_HOLD는 승인 완료 경로에서만 호출됨. 전송 상태 전이는 8.3 참조.
- **응답 유실 멱등성**: n8n이 실제 처리를 완료한 뒤 HTTP 응답만 유실·timeout된 경우에도 동일 action_id 재시도로 모의 MES·메일 효과가 중복 발생하지 않아야 한다. send_action은 action_id를 멱등 키로 n8n에 전달하며, n8n은 이미 처리한 action_id에 대해 downstream 작업을 다시 실행하지 않고 기존 처리 결과를 반환한다. 멱등 키 저장·조회 방식은 시스템 설계서에서 정한다.

### 6.5 generate_analysis_plan — 구현·사용 D (독립)

멘토 원안의 핵심 Agent Tool 4종(`get_fdc_summary`, `get_equipment_context`, `search_documents`, `send_action`)에, 확정된 Text2SQL의 **SQL+통계+차트 계획을 구조화된 Function Calling 계약으로 평가·재사용**하기 위해 D의 독립 Analytics Tool 1종을 추가하여 전체 Tool을 5종으로 관리한다. `generate_analysis_plan`은 초기 LangGraph 호출 대상이 아니므로 `AGENT_MAX_TOOL_CALLS`에 포함하지 않고 독립 실행 결과를 `nl_query_log`에 기록한다. LangGraph 연결은 스트레치 범위다.

```
입력: question: str (자연어)
출력: {ok, sql, metric:{type, column, p?}, group_by:[...],
      visualization:{chart_type, x, y}, reason}
```
- metric.type ∈ {count,sum,mean,median,std,min,max,percentile,ratio} / chart_type ∈ {table,bar,line,histogram}
- LLM은 계획 문자열만 생성. 검증(FR-D-02)·실행(FR-D-03)은 백엔드 코드 담당. LangGraph 연결은 스트레치.

|---|---|---|---|
| 1 | R03_CONSEC 발생 | EQP_HOLD | **필요** |
| 2 | **동일 incident(`lot_id`, `chamber_id`) 내 DISTINCT wafer_no 기준 OOS 3 WAFER 이상**(알람 건수가 아님 — 한 WAFER가 복수 RECIPE STEP에서 OOS 시 알람은 다건) | LOT_HOLD | 자동 |
| 3 | **동일 incident 내 OOS 1~2 WAFER** | NOTIFY | 자동 |
| 4 | **동일 incident 내 OOC만 발생** | MONITOR | 자동 |

- **조치 단위(incident) 정의**: 알람은 WAFER 단위로 발생하지만 **조치는 LOT·챔버 단위(incident)**로 수행한다(TROUBLE 5장의 “조치는 LOT 단위” 원칙을 챔버까지 좁혀 적용). **incident key는 `(lot_id, chamber_id)`로 확정하며, 위 결정표의 OOS·OOC는 모두 동일 incident 범위에서 계수한다.** 동일 incident의 알람은 자동 배치에서 먼저 전체를 집계한 뒤 위 결정표의 최고 우선순위 조치 **1건만** 생성·전송한다(FR-C-14). 동일 incident에 서로 다른 센서의 알람이 함께 존재하더라도 조치는 1건으로 통합한다. 중복 방지의 구현 방식(고유 인덱스·advisory lock·원자적 생성 등)은 시스템 설계서(8/14)에서 확정한다
- **조치 이력 생성 시점(확정)**: decide_action이 incident의 조치를 확정하면 전송·승인 여부와 관계없이 action_history 행을 즉시 1건 생성한다. 자동 조치는 `approval_status=AUTO, send_status=WAITING, approved_by='system', approved_at=created_at`으로 생성한 뒤 전송하고, EQP_HOLD는 `approval_status=PENDING, send_status=WAITING, approved_by=NULL, approved_at=NULL`인 action_history와 `status=PENDING`인 approval_request를 같은 트랜잭션에서 생성한 뒤 Agent를 중단한다. 순수 연쇄 이상에 따른 조치 생략만 action_history를 생성하지 않는다

> **역할분담 문서와의 정책 정합**: 역할분담 v9.3 11.2의 “승인·반려 결정 시 action_history 생성” 문구보다 본 요구사항의 **조치 결정 시 선생성·승인 시 기존 행 갱신** 규칙을 우선 적용한다. 배포 데이터의 ACT-0005·ACT-0010이 승인 전 `PENDING/WAITING` 상태로 존재하고, FR-C-14의 승인 결정 전 10개 incident·10개 조치 재현에 선생성이 필요하기 때문이다. 역할 소유권은 변경하지 않으며, 역할분담 v9.5에는 본 규칙을 유지하여 두 문서를 일치시켰다.

- **반복 LOT 상향 조건(확정)**: 동일 챔버에서 동일 `(sensor_id, recipe_step_no, rule_id)` 알람이 직전 처리 LOT과 현재 LOT의 **2개 연속 LOT**에서 발생하면 반복 이상으로 판정한다. LOT 처리 순서는 챔버별 최초 `chamber_wafer_cum`으로 판정한다. 기본 조치를 한 단계 상향하되 이 조건만으로는 **LOT_HOLD를 초과하지 않는다**. R03_CONSEC가 있으면 반복 조건과 무관하게 EQP_HOLD를 적용한다
- **하류 공정 전파 상향 조건(확정)**: 동일 `lot_id + wafer_no`에 대해 Neo4j `NEXT_STEP` 관계상 하류 공정의 `lot_history.track_in_at <= alarm.occurred_at`인 경우에만 **알람 발생 시점에 이미 하류로 전파된 것**으로 판정한다. 현재 DB에 하류 이력이 존재한다는 사실만으로는 상향하지 않는다. 기본 조치를 한 단계 상향하되 이 조건만으로는 **LOT_HOLD를 초과하지 않는다**. **배포 데이터에서는 모든 PHOTO 알람이 하류 ETCH 투입보다 먼저 발생하여 본 조건이 성립하는 사례가 없으므로, 합성 fixture를 사용한 decide_action 단위 테스트로만 검증하고 골든 시나리오에는 포함하지 않는다. 판별 시점을 조치 결정 시각으로 변경하면 LOT-260006이 MONITOR에서 NOTIFY로 상향되어 배포 정답과 어긋나므로 기준 시점은 `alarm.occurred_at`으로 고정한다**
- **CD_AEI FAIL 상향 예외(확정)**: "직접 연결"은 `alarm.lot_id = metrology.lot_id` AND `alarm.wafer_no = metrology.wafer_no` AND `metrology.measure_type = 'CD_AEI'` AND `metrology.judgement = 'FAIL'`인 계측 결과를 의미한다. 해당 FAIL이 상류 기여의 근거로 사용되거나 다른 WAFER의 결과인 경우 하류 조치 상향에 중복 적용하지 않는다. 순수 연쇄 이상에서는 조치 생략 규칙을 우선한다 (근거: 계측은 LOT당 WAFER 1·6에만 존재하므로 ALM-0031은 w3, CD_AEI FAIL은 w1 → 조인 공집합 → 상향 없이 MONITOR = ACT-0006)
- **CD_AEI 상향 상한 규칙(확정)**: 동일 LOT·동일 WAFER의 CD_AEI=FAIL이 알람과 직접 연결되면 기본 조치를 한 단계 상향한다. 단, **CD_AEI FAIL에 의한 상향 결과는 최대 LOT_HOLD로 제한한다.** EQP_HOLD는 R03_CONSEC 또는 별도로 확정된 챔버 수준 이상 근거가 있을 때만 적용한다. 이미 기본 조치가 EQP_HOLD이면 그대로 유지한다 (근거: ACT-0003=LOT_HOLD(LOT-260005, w6 FAIL 직접 연결에도 EQP_HOLD 아님)·ACT-0008=LOT_HOLD(LOT-260009 동일 패턴)·ACT-0002=EQP_HOLD(R03 근거). 계측 FAIL은 LOT 품질 문제이지 챔버 이상의 단독 증거가 아님 — anomaly_score가 단독으로 EQP_HOLD를 못 만드는 것과 같은 원칙)
- **CD_AEI 관련 decide_action 적용 순서(확정)**: ① 순수 연쇄 이상이면 조치 미생성 → ② R03_CONSEC 등 챔버 수준 근거가 있으면 EQP_HOLD → ③ 그 외에는 기본 결정표로 조치 결정 → ④ 동일 WAFER의 CD_AEI FAIL이 있으면 한 단계 상향하되 LOT_HOLD로 제한
- **CD_AEI 상향 단위 테스트 4건(FR-C-03에 포함)**: ⑴ 미성립 — ALM-0031(w3)+FAIL(w1) → 조인 공집합 → MONITOR(=ACT-0006) ⑵ 성립+상한 — ALM-0013(w6)+FAIL(w6) → 기본 LOT_HOLD 유지(=ACT-0003) ⑶ 챔버 근거 우선 — LOT-260004 R03 → EQP_HOLD 유지(=ACT-0002) ⑷ **합성 fixture** — 기본 NOTIFY + 동일 WAFER CD_AEI FAIL → LOT_HOLD 상향 (배포 데이터만으로는 상향 로직 미구현도 통과 가능하므로 상향 발동 자체를 검증)
- **OOS 계수 경계 테스트 2건 세트(FR-C-03에 포함)**: **[배포 양성 경계]** LOT-260009/ETC-01-C1 — OOS 알람 3건 = 고유 WAFER 3장 → LOT_HOLD **[합성 음성 경계]** R03 없이 OOS 알람 3건이 고유 WAFER 2장에만 발생한 fixture → NOTIFY (알람 행 수로 계수한 구현은 LOT_HOLD를 반환해 실패해야 함. fixture 근거: LOT-260009/PHO-01-C1 w7의 ALM-0038(EXPOSE)+ALM-0039(DEVELOP) 동일 WAFER 이중 알람 실재 패턴. 배포 데이터 10그룹 전부 알람 수·고유 WAFER 수 판정이 일치해 음성 fixture 없이는 검증력 없음)
- 하향 조건 — 두 경우를 구분한다:
  - **순수 연쇄 이상**: CD_AEI FAIL이지만 **ETCH 센서 4종이 모두 IN_CONTROL(=OOC/OOS 0건)**이고 같은 WAFER의 PHOTO OOS가 확인되면, 하류 ETCH 장비에는 별도 조치를 생성하지 않는다. agent_run.recommended_action=NULL, action_history 미생성으로 처리하며, 상류 PHOTO 원인과 LOT_HOLD 조치 및 판단 근거를 agent_run.action_reason과 audit_log에 기록한다 (TROUBLE 4.1 절차 ②·5.3. 판별은 WAFER 단위, 조치는 LOT·챔버 incident 단위)
  - **복합 이상**: 하류 장비에도 자체 OOC/OOS 알람이 존재하면 상류 기여를 함께 제시하되, **하류 조치는 해당 알람의 조치 결정표(위 우선순위)를 그대로 적용**한다. 하류에 R03_CONSEC이 발생했다면 하류 장비도 EQP_HOLD 대상이다(배포 데이터에는 이 조합 사례가 없으나 규칙은 열어 둔다). LOT-260008은 ETCH에 R03 없이 ET_CF4 OOC만 존재하므로 MONITOR이며 EQP_HOLD를 적용하지 않는다
  - 단발 발생 후 정상 복귀 시 MONITOR — **정상 복귀 = 현재 이상 WAFER 다음으로 해당 챔버에서 실제 처리된 바로 다음 WAFER를 `chamber_wafer_cum` 순서로 먼저 선택하고, 그 WAFER의 동일 `(chamber_id, sensor_id, recipe_step_no)` 요약이 IN_CONTROL로 복귀한 경우**다(TROUBLE 5.3 원문 "다음 WAFER가 정상으로 돌아왔다" 기준). 바로 다음 실제 WAFER에 동일 키 요약이 없으면 하향하지 않으며, 이후의 같은 키 관측까지 중간 WAFER를 건너뛰어 찾지 않는다. 반복 LOT·하류 전파·CD_AEI 직접 연결 중 하나라도 성립하면 정상 복귀 하향은 적용하지 않는다
- **조건 충돌 최종 우선순위(확정)**: ① 순수 연쇄 이상이면 하류 조치 미생성 → ② R03_CONSEC이면 EQP_HOLD → ③ 기본 결정표 적용 → ④ CD_AEI 직접 연결·반복 LOT·하류 전파가 있으면 한 단계 상향하되 최대 LOT_HOLD → ⑤ 상향 조건이 없고 단발 후 다음 WAFER가 정상 복귀하면 MONITOR. 여러 상향 조건이 동시에 성립해도 단계는 한 번만 올린다
- **반복 LOT·정상 복귀 fixture(필수)**: 반복 LOT 양성은 직전 처리 LOT과 현재 LOT의 동일 `(chamber_id, sensor_id, recipe_step_no, rule_id)` 알람으로 기본 NOTIFY가 LOT_HOLD로 상향되는지 검증한다. 중간 처리 LOT이 있거나 키 하나가 다르면 상향하지 않는 음성 fixture도 함께 둔다. 정상 복귀 양성은 기본 NOTIFY인 현재 이상 WAFER의 **챔버상 바로 다음 실제 처리 WAFER**에 동일 `(chamber_id, sensor_id, recipe_step_no)` 요약이 있고 IN_CONTROL일 때 MONITOR로 하향되는지 검증한다. 바로 다음 WAFER가 OOC/OOS, 동일 키 요약 없음, 다음 실제 WAFER 없음, 키 불일치, 중간 WAFER를 건너뛴 뒤에만 동일 키 IN_CONTROL 존재 또는 상향 조건 동시 성립 시 하향하지 않는 음성 fixture를 함께 둔다. 상세 정렬·조회 DTO는 시스템설계서 v1.2에서 확정한다
- anomaly_score(`SEVERITY_HIGH_THRESHOLD=0.80`)는 **보조 신호**로만 사용하며 단독으로 EQP_HOLD를 유발하지 않는다
- 본 규칙은 **코드(decide_action 함수)로 구현하며 LLM에 위임하지 않는다** — 승인 게이트가 확률적으로 동작하면 안전장치가 아니기 때문
- **send_channel 매핑(조치→전송 채널)**: MONITOR·NOTIFY → **EMAIL** / LOT_HOLD·EQP_HOLD → **MES** (v9.3 11.2 확정, 배포 데이터 action_history 패턴과 일치). send_action(6.4)이 action_id만 받으므로 **action_history 행 생성 시점에 채널이 확정**되어야 한다

### 8.3 승인·반려·전송 상태 규칙 (HITL)

- EQP_HOLD만 사람 승인 대상. 승인 전 전송 불가(send_action은 승인 완료 경로에서만 호출)
- 승인 큐 단일 소스: approval_request. 승인/반려는 조건부 갱신으로 이중 처리를 차단하고, 기처리 건(APPROVED/REJECTED/**EXPIRED**) 재요청은 409로 응답:

> 승인 요청을 시간 경과로 `EXPIRED`로 바꾸는 스케줄러는 초기 범위 밖이다. `EXPIRED`는 기존 데이터 또는 격리 테스트 fixture에 존재할 수 있는 터미널 상태로만 취급하며, 승인 API는 관련 approval_request·agent_run·action_history를 변경하지 않고 409를 반환한다.

```sql
UPDATE approval_request
SET ...
WHERE approval_id = :approval_id
  AND status = 'PENDING'
RETURNING ...;
-- 변경된 행이 없으면 409 Conflict
```

- **승인 요청 생성 트랜잭션**: EQP_HOLD 결정 시 agent_run을 WAITING_APPROVAL로 전환하고, action_history(`approval_status=PENDING, send_status=WAITING`)와 approval_request(`status=PENDING`)를 함께 생성하며 APPROVAL_REQUESTED 감사로그를 기록한다. 이 트랜잭션이 커밋된 뒤 LangGraph를 interrupt한다
- **승인 결정 트랜잭션 범위**: 승인·반려 결정 시 approval_request 상태, agent_run의 WAITING_APPROVAL → RUNNING 전환, **기존 action_history의 승인·전송 상태와 승인자 필드**, APPROVAL_DECIDED 감사로그만 갱신·기록한다. 새 action_history 행은 생성하지 않는다. 승인 시 approval_request의 `decided_by/decided_at`을 기존 action_history의 `approved_by/approved_at`에 복사하고 `APPROVED/WAITING`으로 갱신한 뒤, 커밋 후 LangGraph를 재개하여 send_action을 호출한다. 반려 시 기존 행을 `REJECTED/CANCELED`로 갱신하되 `approved_by/approved_at`은 NULL로 유지하고, 반려 행위자는 approval_request와 audit_log에 기록하며 전송하지 않는다. **전송 결과와 agent_run의 최종 상태(COMPLETED/FAILED) 및 ended_at은 후속 트랜잭션에서 기록한다**

**경로별 상태 전이**

| 경로 | approval_request | agent_run.status | action_history.approval_status | action_history.send_status | send_action |
|---|---|---|---|---|---|
| 승인 | PENDING → APPROVED | WAITING_APPROVAL → RUNNING → COMPLETED (전송 실패 시 FAILED) | PENDING → APPROVED (`approved_by=decided_by`, `approved_at=decided_at`) | WAITING → SENDING → SENT (실패 시 FAILED) | 승인 커밋 후 호출 |
| 반려 | PENDING → REJECTED | WAITING_APPROVAL → RUNNING → COMPLETED | PENDING → REJECTED (`approved_by/approved_at=NULL`) | WAITING → CANCELED (기존 행 갱신) | 미호출 |
| 자동조치 | (미생성) | RUNNING → COMPLETED (전송 실패 시 FAILED) | AUTO (`approved_by='system'`, `approved_at=created_at`) | WAITING → SENDING → SENT (실패 시 FAILED) | 행 생성 후 호출 |
| 조치 생략 | (미생성) | COMPLETED (recommended_action=NULL) | (행 미생성) | — | 미호출. **순수 연쇄 이상(ETCH 센서 4종 모두 IN_CONTROL=OOC/OOS 0건 + 같은 WAFER PHOTO OOS)에 한한다.** 사유는 agent_run.action_reason과 audit_log에 기록 |

> 표의 상태 전이 표기(예: WAITING_APPROVAL → RUNNING → COMPLETED)는 **전체 생애주기**를 나타내며 단일 트랜잭션을 뜻하지 않는다. 트랜잭션 경계는 위 「승인 트랜잭션 범위」를 따른다.

**전송 상태 전이**

```
WAITING → SENDING → SENT
WAITING → SENDING → FAILED
WAITING → CANCELED          # EQP_HOLD 반려, 전송 미호출
FAILED  → SENDING          # 재시도 상한 내
SENDING·SENT·CANCELED 상태에서는 재전송하지 않음
```

- FAILED 조치를 재시도할 때는 신규 action_history를 만들지 않고 **동일 action_id의 기존 행을 `FAILED → SENDING`으로 갱신**한다. 전송 이전 Tool 장애처럼 action_history가 생성되지 않은 실패만 수동 재실행에서 신규 조치를 생성할 수 있다
- 프로세스 종료 등으로 SENDING 상태가 고착된 경우의 판별 시간, n8n 처리 결과 조회 및 동일 action_id 기반 복구 절차는 시스템 설계서에서 구체화한다

- 배포 데이터의 action_history 초기 PENDING 2건(ACT-0005·ACT-0010)은 **Text2SQL 검증용 기준 데이터**이며, 1주차 승인 화면 Mock 개발에도 사용할 수 있다. **실제 HITL 승인 대기 목록의 원천은 approval_request**이다

### 8.5 재시도·상한 정의 (AGENT_MAX_RETRY)

`AGENT_MAX_RETRY=3`은 .env.example의 **기존 변수**이며, 의미를 다음으로 확정한다: **Tool 호출의 내부 재시도 횟수로, 최초 호출 이후 최대 3회 재시도(동일 Tool 호출 최대 4회 시도)**. `AGENT_MAX_TOOL_CALLS=8`은 재시도를 포함한 그래프 1회 실행의 총 Tool 호출 상한이며, 동일 Tool 최대 4회 시도는 총 상한의 잔여 횟수 안에서만 가능하다(총 상한 도달 시 재시도 잔여와 무관하게 중단). 조치 생성 가능 경로는 진단 단계부터 최초 `send_action` 1회분을 예약하고 선택 조회가 이를 소비하지 못하게 하며, HITL checkpoint 재개 또는 checkpoint 유실 복구 후에도 영속 호출 이력에서 누적 수를 복원한다. 전송 재시도는 예약된 최초 호출 후 남은 총예산과 Tool별 재시도 한도를 동시에 적용한다. 단계별 예산·영속화 방식은 시스템설계서 v1.2에서 정의한다. **두 값 모두 agent_run 단위의 재처리(FR-C-09)와는 무관하다.** 문서·코드·단위 테스트에서 동일 정의를 사용한다.


## 9. Text2SQL 질의셋 【멘토 요구 ⑤】

평가 방법: SQL 문자열이 아닌 **실행 결과를 비교하고, 통계·시각화를 요구한 문항은 구조화된 분석 계획도 함께 비교**한다. 기대 결과는 배포 데이터 검증값을 기준으로 한다.

- 정수·문자열·ID 집합은 기대 결과와 정확히 비교한다
- 평균·비율 등 실수 결과는 기준값과의 절대오차가 **0.001 이하**이면 일치로 판정한다
- 기본적으로 결과 행 순서는 무시하되, 질문에 정렬 방향이 명시된 경우(예: #4 내림차순)는 순서까지 비교한다
- 시각화를 요구한 질문은 실행 결과와 함께 `visualization.chart_type`, `x`, `y`가 모두 요구 의도와 일치해야 정답으로 판정한다. #9는 `chart_type=line`이며 시간·순서 컬럼을 x, PH_FOCUS 측정값을 y로 사용해야 한다

평가 전제: Text2SQL은 13장의 **Text2SQL 평가 DB**에서 평가한다. 해당 DB의 16개 평가 대상 base table은 `action_history` 10건을 포함한 교육생 배포패키지 초기 적재 상태를 유지한다. `nl_query_log`에는 평가 이력을 누적할 수 있으나 골드 기대값·기준 hash 대상에서는 제외한다. Agent E2E DB와 분리 운영하므로 Agent·승인 테스트 결과는 골드 질문 기대값에 영향을 주지 않는다.

### 9.2 방어 케이스 (6) — 전부 안전하게 차단·처리되어야 통과

| # | 입력 | 차단 지점 |
|---|---|---|
| D1 | "알람 테이블 전부 지워줘" | SELECT 외 구문 거부(sqlglot) |
| D2 | "SELECT 1; DROP TABLE fdc_alarm" | 다중 문장 거부 |
| D3 | document_chunk 조회 요청 | 화이트리스트 외 테이블 거부 |
| D4 | 존재하지 않는 컬럼 질의 | 컬럼 검증 또는 실행 오류의 정상 처리(ok:false) |
| D5 | `SELECT pg_sleep(10)` | 위험 함수 차단. FROM 절이 없어도 함수 AST를 검사하여 실행 전에 거부 |
| D6 | `SELECT * FROM pg_catalog.pg_tables` | 시스템 카탈로그 접근 차단. 스키마 한정 테이블명을 정규화하여 검사 |

Text2SQL 화이트리스트: 기준정보 10종 + 생산 데이터 6종 (에이전트·감사·문서 테이블, 시스템 카탈로그 제외 — 전용 API로만 노출). 위험 함수 차단, DB 내부 오류·접속정보 비노출.

**제한적 교정 재생성 규칙**

- 읽기 의도인데 생성 SQL이 구문 오류·스키마 불일치·존재하지 않는 컬럼으로 검증에 실패한 경우에만 오류 사유를 반영해 **1회 재생성**한다(최초 생성 포함 최대 2회)
- 쓰기·DDL 의도, 다중 문장, 비허용 테이블, 위험 함수, 시스템 카탈로그 접근은 정책 위반이므로 재생성하지 않고 즉시 거부한다
- 두 번째 SQL도 9.2 전체 검증을 다시 통과해야 하며 실패하면 실행하지 않고 `{ok:false, reason}`을 반환한다. 이 재생성 횟수는 D 파이프라인 내부 제한이며 `AGENT_MAX_RETRY`를 사용하지 않는다
- 검증기는 최상위 노드가 `SELECT`인지 보는 데 그치지 않고 CTE·서브쿼리까지 AST를 재귀 순회하여 INSERT·UPDATE·DELETE·DDL·SELECT INTO·잠금 구문 등 쓰기 효과가 있는 노드를 차단한다

**테스트 데이터 격리 원칙**

- **Text2SQL 평가 DB**의 16개 평가 대상 base table은 배포 초기 상태를 유지하며 `action_history` 10건(승인 대기 2건 포함)을 적재한다. 9장의 기대 결과는 이 base table 상태를 기준으로 채점한다. 평가 이력용 `nl_query_log` 누적은 허용하되 기준 데이터·content hash에서 제외한다
- 위 분리는 **골드 평가 격리 원칙**이다. 일반 운영 `/analytics/query`와 `nl_query_log`는 Agent·승인·감사 기능이 사용하는 운영 DB의 최신 허용 테이블을 읽고 기록하며, 평가 one-shot만 별도 Text2SQL 평가 DB 연결을 사용한다. `approval_request`·`audit_log`는 Text2SQL allowlist 밖이므로 해당 질문은 정책 거부하고 전용 승인·감사 화면/API로 안내한다
- **Agent E2E DB**는 `fdc_alarm` 51건 등 입력 데이터는 유지하되, 실행 시작 시 `action_history`·`agent_run`·`agent_run_alarm`·`agent_tool_call`·`approval_request`·`audit_log`·`action_delivery`·**운영 `nl_query_log`**와 Checkpoint 실행 데이터를 빈 상태로 둔다(`checkpoint_migrations`는 보존). 운영 `nl_query_log`는 운영 DB에 함께 있으므로 초기화 대상이며, 평가 DB의 `nl_query_log`는 초기화하지 않는다
- ACT-0001~0010은 Agent E2E 대상 `action_history`에 적재하지 않고 CSV·JSON 또는 별도 expected fixture로 보관하여 신규 생성 조치 10건과 비교한다
- Agent E2E는 별도 테스트 DB·스키마 또는 매 실행 전 초기화가 보장되는 격리 환경에서 수행한다. 공용 DB의 초기 정답 데이터를 삭제하거나 덮어쓰지 않는다
- Text2SQL 평가 DB와 Agent E2E DB는 목적과 초기 상태가 다르므로 동일 DB 상태를 공유하지 않는다

## 부록 B. 골든 시나리오 상세

**공통 실행 전제**: 골든 시나리오는 `fdc_alarm` 51건 등 입력 데이터는 유지하되 `action_history`·`agent_run`·`agent_run_alarm`·`agent_tool_call`·`approval_request`·`audit_log`·`action_delivery`·운영 `nl_query_log`와 Checkpoint 실행 데이터가 빈 Agent E2E DB에서 실행한다. ACT-0001~0010은 대상 테이블에 적재하지 않고 별도 expected fixture로만 사용한다.

**FR-C-10 ALM-0031 복합 이상 E2E 추가 전제**: 같은 빈 Agent E2E DB에서 LOT-260008 PHOTO incident를 먼저 처리해 LOT_HOLD 조치를 신규 생성한 뒤 ALM-0031을 실행한다. 이 선행 조치는 expected fixture ACT-0007과 조치 코드·incident가 대응하지만 실제 action_id는 새로 생성하며, ACT-0007 원본 행을 DB에 미리 적재하지 않는다.

위 선행 처리 순서는 **ALM-0031 단독 시나리오의 재현 절차**일 뿐 전체 자동 배치의 실행 순서를 고정하지 않는다. 전체 51건 배치는 incident 순서를 바꾸어도 모든 incident의 판단 결과를 이용할 수 있어야 하며, ALM-0031 분석 결과에는 항상 같은 LOT의 상류 PHOTO LOT_HOLD 판단 근거가 포함되어야 한다. 구현은 시스템설계서 v1.2 4.3에서 확정한 **1단계 전체 incident 계획 계산 → 2단계 Agent 실행·근거 결합** 방식을 사용하며, 이는 본 요구사항의 실행 순서 독립성을 구현하는 내부 설계다.

### 시나리오 1. 자동조치 성공

- 입력 alarm_id: **ALM-0001** (LOT-260003 / R02_OOC)
- 예상 action_code: **MONITOR**
- 예상 send_channel: **EMAIL**
- 검증: action_history.approval_status=AUTO, `approved_by='system'`, `approved_at=created_at`, 최종 send_status=SENT
- **agent_run.status = COMPLETED, ended_at 기록, AGENT_RUN_COMPLETED 감사로그 기록**

### 시나리오 2. EQP_HOLD 승인

- 입력 R03 alarm_id: **ALM-0022** (LOT-260007 / PHO-01-C1)
- 검증: 조치 결정 시 action_history `PENDING/WAITING`과 approval_request `PENDING`이 함께 생성되고, 승인 시 기존 action_history가 `APPROVED/WAITING`으로 갱신되며 `approved_by=decided_by`, `approved_at=decided_at`이 일치한 뒤 send_status `SENDING → SENT`, n8n 모의 전송 정확히 1회
- **agent_run.status = WAITING_APPROVAL → RUNNING → COMPLETED 전이 확인, AGENT_RUN_COMPLETED 감사로그 기록**

### 시나리오 3. EQP_HOLD 반려

- 입력 R03 alarm_id: **ALM-0048** (LOT-260010 / ETC-01-C1)
- 검증: 조치 결정 시 action_history `PENDING/WAITING`과 approval_request `PENDING`이 함께 생성되고, 반려 시 새 조치 행을 만들지 않고 기존 행을 `REJECTED/CANCELED`로 갱신하며 `approved_by/approved_at`은 NULL 유지, n8n 미호출
- **agent_run.status = WAITING_APPROVAL → RUNNING → COMPLETED 전이 확인, ended_at 기록, APPROVAL_DECIDED·AGENT_RUN_COMPLETED 감사로그 기록**

### 시나리오 4-A. Tool 장애 (조치 전송 이전)

- 실패 주입 방법: 격리 테스트 환경에서 잘못된 Neo4j URI, dependency override 또는 Tool mock으로 `{ok:false, reason}` 반환. **공용 서버 컨테이너는 중지하지 않는다**
- 검증:
  - Tool은 예외를 던지지 않고 {ok:false, reason} 반환 (NFR-09)
  - agent_tool_call.status = ERROR 또는 TIMEOUT, error_msg 기록
  - 재시도 상한(8.5) 소진 후 agent_run.status = FAILED, AGENT_RUN_FAILED 감사로그 기록
  - **조치 전송 이전이므로 action_history 행과 ACTION_SEND_FAILED는 기록하지 않는다**
  - API 프로세스 생존 (NFR-16)

### 시나리오 4-B. n8n 전송 장애 (승인 이후)

- 실패 주입 방법: 격리 테스트 webhook이 HTTP 500 또는 timeout을 반환하도록 구성. **공용 서버 컨테이너는 중지하지 않으며**, 컨테이너 중지 검증은 별도 테스트 Compose 스택에서만 수행
- 검증:
  - **승인 트랜잭션은 이미 커밋되어 롤백되지 않는다**(8.3). approval_request.status = APPROVED 유지
  - **agent_tool_call.status = ERROR 또는 TIMEOUT** (n8n 전송은 send_action Tool 내부에서 수행되므로 전송 실패 = 해당 Tool 호출 실패)
  - action_history.send_status = FAILED
  - ACTION_SEND_FAILED 감사로그 기록
  - 재시도 상한 소진 후 agent_run.status = FAILED
  - 내부 재시도와 FAILED 수동 재실행 모두 기존 action_history의 동일 action_id를 사용하며 신규 조치 행을 생성하지 않음
  - 동일 action_id 재시도 시 중복 전송 미발생. 특히 n8n이 모의 발송을 처리한 뒤 응답만 timeout되는 fixture에서 재시도해도 downstream 효과는 총 1회 (FR-C-06·09·12)
  - FR-D-07 감사로그 화면에서 실패 이벤트 조회 확인 (D 검증 관점)

> 순수 연쇄 이상 규칙은 유일한 해당 케이스(LOT-260008 w1)에 트리거 알람이 없어 **E2E 검증이 불가능**하므로, 골든 시나리오에 포함하지 않고 decide_action 단위 테스트(FR-C-03·FR-C-10)로만 검증한다.

### C.2 시스템 설계서로 이월하는 구현 상세

- incident 중복 방지를 부분 고유 인덱스·advisory lock·트랜잭션 중 어떤 방식으로 구현할지와 동시 실행 잠금 순서
- 부분 고유 인덱스 채택 시 `send_status IS DISTINCT FROM 'CANCELED'` 조건 및 별도 마이그레이션 SQL
- incident 처리 시작 시 포함된 모든 alarm_id를 다음 자동 배치의 선택 대상에서 제외하는 완료·포함 관계 저장 방식. 런타임은 incident당 agent_run 1건으로 고정하므로 `agent_run.alarm_id`에 저장할 대표 alarm_id의 결정론적 선택 규칙과 전체 alarm_ids를 State·evidence_json·별도 연결 테이블 중 어디에 보존할지 함께 확정
- 전체 51건 배치에서 incident 처리 순서와 무관하게 연쇄 근거를 결합하는 방식. 시스템설계서 v1.2 4.3은 1단계 전체 incident 계획 계산 후 2단계 Agent 실행·관계 근거 결합 방식으로 구체화하며 ALM-0031 순서 섞기 테스트로 검증
- `approval_request`에 action_id·chamber_id가 없으므로 승인 API가 대상 action_history를 유일하게 찾는 연결 방식. `approval_request.agent_run_id → agent_run(lot_id·chamber_id) → 해당 incident의 유효 action_history` 조회 규칙 또는 LangGraph State의 action_id 보존 방식을 확정하고 동시 승인 시 모호성이 없음을 보장
- incident 내 다수 알람 중 `action_history.trigger_alarm_lot_hist_id`에 기록할 대표 lot_hist_id의 결정론적 선택 규칙. 단순 R03 알람 행과 배포 expected fixture의 trigger 값이 항상 같지 않으므로 조치 우선순위·시간·ID 등을 이용한 타이브레이크와 fixture 비교 범위를 명시
- `fdc_summary`의 WAFER당 복수 센서·RECIPE STEP 행을 `get_fdc_summary`의 WAFER당 단일 anomaly_score로 만드는 feature pivot·집계 규칙과 누락 센서 처리, 정확히 1개 점수를 반환하는 계약
- 운영 데이터에서 `chamber_wafer_cum`이 중복될 때의 R03 보조 정렬 키와 연속 상태 저장 방식
- n8n의 action_id 멱등 키 저장·조회 방식과 timeout 응답 유실 처리. 프로세스 종료 등으로 SENDING 상태가 고착됐다고 판정하는 시간과 n8n 처리 결과 조회·동일 action_id 복구 절차
- Neo4j·n8n 장애 주입용 dependency override·mock webhook·별도 Compose 구성
- IsolationForest 최종 feature 목록, 정상 전용 또는 전체 표본 학습 방식, 평가 실행 절차
- PostgreSQL Checkpoint 초기화 절차: `PostgresSaver.setup()`이 생성·변경하는 테이블 목록, 실행 계정, 공용 DB 최초 1회 실행 시점, 애플리케이션 시작 시 자동 DDL 금지, 재실행 안전성 검증과 실패 시 복구 절차. 배포 `01_schema.sql`은 수정하지 않고 별도 마이그레이션·운영 절차로 관리
- Text2SQL 테이블 검증 시 sqlglot `Table` 노드의 `catalog + db + name`을 정규화하여 전체 식별자로 검사하는 방식. 시스템 테이블 거부 목록에 의존하지 않고 애플리케이션 허용 테이블만 통과시키는 allowlist를 적용하며, `pg_class`처럼 스키마가 생략된 시스템 테이블도 허용 목록에 없으면 거부. CTE·서브쿼리를 포함한 AST 전체를 재귀 순회하여 쓰기·DDL·SELECT INTO·잠금 노드를 차단하는 구체적 노드 목록과 검증 순서를 명시
- 모노레포 루트 `docker-compose.yml`에서 사용할 PostgreSQL/pgvector·Neo4j·n8n·Backend·Frontend 전체 이미지 태그와 digest, `backend/`·`frontend/` build context, Frontend Node 고정 버전, 패키지 설치·빌드 절차. n8n만이 아니라 통합 Compose의 모든 서비스가 재현 가능해야 함
- Agent Level 1·2 비교에 사용할 고정 시나리오 집합, 반복 횟수, 완료율·평균 Tool 호출 수·지연시간·토큰 사용량 집계 방법
- `agent_run.latency_ms` 측정 경계: 시작·종료 시점, 여러 LLM·Tool 호출의 합산 방식, 오류 실행 기록 방식과 HITL 사람 대기시간 제외 방법. Level 1·2 비교는 자동조치 또는 승인 응답을 고정한 fixture로 사람 반응시간의 영향을 제거
- nullable incident key backfill·원본 식별자 정합 검사·NOT NULL 전환 후 부분 고유 인덱스를 생성하는 migration 순서와 검증
- 운영 Text2SQL과 평가 one-shot의 DSN·로그 pool·Compose 환경 주입 분리, 평가 source hash·기준 건수 사전검증과 runtime fallback 금지
- `agent_tool_call` 영속 시도 예약을 기준으로 8회 예산을 복원하고 최초 `send_action`을 예약하는 방식, checkpoint 유실 복구의 잔여 예산 처리
- 공용 교육장 서버의 원본 스키마를 수정하지 않는 최소권한 role 4종·기본 자격증명 전환, 기존 pool 종료와 허용/금지 권한 재검증
- API DTO, LangGraph State·Node·Edge, Repository 구조와 트랜잭션 경계의 구체적 구현

위 항목은 본 문서에서 확정한 사용자 관점 동작과 수용 기준을 변경하지 않는 범위에서 시스템 설계서에 구체화한다. 설계 과정에서 기능 범위나 결과가 달라질 경우 요구사항 정의서를 먼저 개정한다.
