## 0. 문서 목적과 기준 우선순위

본 문서는 제공 최종 패키지를 현재 프로젝트의 데이터·동작 기준으로 채택할 때 필요한
구현 구조, 데이터 격리, 상태 전이, API·Tool, 자동화, 평가·복구 계약을 정의한다.
v2.0 작업본은 전환 이력으로 보존하되 신규 구현의 기준으로 사용하지 않는다.

최종 패키지는 데이터 전용 압축이 아니라 참고 Backend·Frontend·node_modules까지 포함한
전체 프로젝트 snapshot이다. 저장소에는 압축 전체를 복사하지 않고 다음 allowlist만
검증·승격한다.

- sample/data의 CSV 9개
- sample/schema/03_schema_clean.sql
- sample/ontology/master.cypher
- sample/rag의 문서 3개
- mvp/gen_sample_data.py
- 최종 동작을 설명하는 00_README.md, 검토질문_답변.html과 필요한 가이드

RAG 저장·적재에 ③에 없는 구성은 교육생 배포패키지①에서 선별한다. ①의
`document`·`document_chunk`·vector extension, `load_documents.py`,
`BAAI/bge-m3`·1024만 사용하며, ①의 다른 table·RAG 문서·graph는 승계하지 않는다.
base 9 table·RAG 원문·`master.cypher`는 위 최종 패키지③이 정본이다.

### 0.1 충돌 해결 순서

사용자 동작은 요구사항정의서가, 구현 구조는 본 설계서가 우선한다. 최종 패키지 내부에서
수치·schema가 충돌하면 다음 순서로 판정한다.

1. 실제 CSV header·row·값과 03_schema_clean.sql의 물리 형식
2. 동일 결과를 byte 단위로 재생성하는 gen_sample_data.py
3. 실측 재계산 결과와 master.cypher의 실제 graph
4. 실제 frontend/src와 backend/app의 호출·화면 구현
5. 검토질문_답변.html과 00_README.md의 최종 동작 설명
6. 02_화면별_API_가이드.md·04_알람_재현_가이드.md·05_검토질문_답변.md 등 Markdown 설명

따라서 Markdown에 남은 TRACE 126, SUMMARY 47, evaluation OOS 42, action 10 같은 값은
구 이력이며 구현·수용 기준으로 사용하지 않는다. 실제 CSV와 Generator가 확정한
TRACE 138, SUMMARY 51, evaluation OOS 46, action 12가 기준이다.

화면도 같은 원칙을 적용한다. 02_화면별_API_가이드.md는 5번째 화면을 자연어 질의로 적지만,
실제 최종 frontend/src/App.jsx는 Dashboard·Alarm History·Agent·Documents·Ontology 다섯
페이지만 등록하고 검토질문_답변.html은 Text2SQL 화면 제거를 명시한다. 따라서 Ontology가
필수 5번째 화면이고 Text2SQL은 선택 확장이다. 자연어 질문 기능은 별도 Analytics 화면이 아니라
Agent 화면의 Chat mode와 POST /agent/ask로 제공한다.

### 0.2 설계 상태

| 표기 | 의미 |
|---|---|
| 최종 데이터 확정 | 물리 artifact와 재생성·재계산 결과가 일치 |
| 프로젝트 설계 | 최종 데이터를 서비스로 구성하기 위한 팀 설계 |

| 선택 확장 | 5개 필수 화면 밖의 기존 기능으로, 필수 경로를 깨지 않는 범위에서 유지 |

### 0.3 핵심 불변식

1. dataset epoch fdc_final_20260818과 source archive hash를 모든 bootstrap·평가 artifact에 기록한다.
2. 최종 CSV 9개의 schema와 값은 보정 대상이 아니다. canonical stage는 값 변경 없이 검증한다.
3. lot_history.fault_code는 공개 합성 평가 라벨이다. 모델 feature, Agent State, Tool, prompt,
   조치 규칙, Runtime Text2SQL 입력으로 노출하지 않는다.
4. 물리 라벨은 NRM·FOC·RFM·MFD·TMD·OTH 6종이고, 이상 incident의 원인 가설 출력은
   FOC·RFM·MFD·TMD·OTH 5종이다.
5. anomaly score는 화면·Agent의 보조 근거일 뿐 action·severity·HITL을 변경하지 않는다.
6. 조치는 R03, TRACE OOS, SUMMARY OOC 규칙만으로 MONITORING·WARNING·EQP_HOLD 중 하나를 정한다.
7. incident key는 lot_id와 chamber_id의 쌍이며 incident당 Runtime action은 최대 1건이다.
8. EQP_HOLD는 사람 승인 전 Kafka MES 이벤트를 발행하지 않는다.
9. 외부 효과는 action_id와 channel의 쌍으로 멱등하게 관리한다.
10. 공용 PostgreSQL·Neo4j의 파괴적 초기화는 명시적 대상 검증과 confirm 없이 실행하지 않는다.

### 2.3 source·canonical manifest

기존 데이터의 누락값을 채우거나 seq_no를 변환하던 correction stage는 폐기한다. 최종 패키지는
dim_parameter 8행, seq_no 0~5, Summary·Metrology 시각을 이미 제공한다.

canonical builder는 다음만 수행한다.

1. source archive SHA-256과 allowlist entry를 검증한다.
2. ZIP slip, symlink, 절대경로, 중복 entry를 거부한다.
3. CSV를 UTF-8-sig로 읽고 header·field count·type·PK·FK를 검증한다.
4. canonical JSON row hash를 Python Unicode code point 순으로 계산한다.
5. 선택적으로 BOM 제거·LF·CSV quoting만 정규화한 mirror를 만들 수 있으나 cell 값·header·행 순서·
   schema를 변경해서는 안 된다.
6. source와 canonical mirror의 typed row hash가 다르면 실패한다.

다음 변환은 금지한다.

- dim_parameter 임시 보정 layer 생성
- Trace seq_no 재채번
- occurred_at·measured_at 생성
- fault_code·action reference 삭제 또는 수정
- column rename·type 추정

manifest는 format_version=4와 아래 필드를 가진다.

~~~text
artifact_type
dataset_epoch = fdc_final_20260818
source_archive_sha256
selected_entry_manifest_sha256
schema_sha256
generator_sha256
canonicalization_version
hash_algorithm
tables:
  columns
  primary_key
  row_count
  content_hash
  included_by_profile
~~~

전체 DSN·계정·비밀번호·사용자 로컬 경로는 기록하지 않는다. generate는 최초 생성과 갱신 모두
confirm을 요구하며 임시 파일을 검증한 뒤 원자적으로 replace한다. 같은 epoch에 다른 hash를
조용히 덮어쓰지 않는다.

### 2.4 DB profile

| profile | 대상 | base table 상태 | action_history |
|---|---|---|---:|
| runtime | kosa_agent | 최종 base/reference | 0 |
| runtime-e2e | kosa_agent_e2e | 최종 base/reference, 매 시나리오 Runtime reset | 0 |
| evaluation | kosa_text2sql | 최종 base/reference와 평가 reference | 12 |

runtime도 물리 table 9개를 생성하지만 action_history.csv는 적재하지 않는다. evaluation은
9개 CSV를 모두 적재하며 action 12건은 fixture_type=REFERENCE로 manifest에 표시한다.
이는 Agent가 생성한 Runtime 이력이 아니며 독립적인 action Gold라고 주장하지 않는다.

시연 Backend는 kosa_agent만 연결하면 된다. E2E와 evaluation DSN은 전용 command에만 주입한다.
같은 공용 PostgreSQL 서버의 서로 다른 database를 사용하므로 host·port는 같아도 된다.

RAG schema·data profile은 다음 단일 matrix를 사용한다.

| DB | `vector`·`document`·`document_chunk` | corrected canonical 문서 | 서비스 readiness |
|---|---|---:|---:|
| `kosa_agent` | 생성 | 3종 적재 | 검사 |
| `kosa_agent_e2e` | 생성 | 3종 적재 | 미검사(E2E command가 별도 검증) |
| `kosa_text2sql` | 생성 | 3종 적재 | 미검사(evaluation command가 별도 검증) |

세 DB의 schema·문서 정본은 같고 Runtime 실행 데이터만 profile에 따라 다르다. RAG 적재 때문에
두 번째 PostgreSQL 서버를 기동하지 않는다.

### 2.5 bootstrap 순서

~~~text
공통
  source archive·manifest 검증
  → final base DDL로 fresh schema 생성
  → profile별 CSV 적재
  → typed row hash·PK·FK·재계산 검증

runtime
  action_history=0 확인
  → final-compatible reference extension
  → final-compatible Agent Runtime migration
  → action/severity pair guard
  → checkpoint setup

evaluation
  action_history=12 확인
  → final-compatible reference extension
  → Agent Runtime migration 미적용

Knowledge
  Neo4j safe loader
  → corrected RAG source·hash 검증
  → ① document schema와 loader adapter 준비
  → 세 PostgreSQL DB에 vector/document/document_chunk schema 생성
  → 세 DB에 같은 canonical 문서 3종 적재

~~~

runner는 database allowlist, expected epoch, host 확인, read/write 권한, 대상 empty/fresh 상태,
명시적 confirm을 검사한다. 이미 populated인 공용 DB에는 자동 drop·truncate·reload하지 않는다.

### 2.6 공개 합성 라벨 격리

fault_code는 Generator가 넣은 공개 합성 라벨이며 production ground truth가 아니다.

| 사용 위치 | 허용 |
|---|---|
| final evaluation runner | 예, prediction hash 고정 후 join |
| 평가 전용 read role | 예 |
| Detection feature builder·threshold fitting | 아니오 |
| Runtime application Repository | 아니오 |
| Agent Tool·State·checkpoint·prompt | 아니오 |
| ActionPolicy | 아니오 |
| 사용자 자연어 SQL | 기본 아니오 |

runtime role은 fault_code를 제외한 명시 column projection만 사용한다. 가능하면
v_lot_history_runtime View와 column-level grant로 차단한다. evaluation role은 prediction artifact를
먼저 고정한 뒤 별도 query에서 라벨을 결합한다. label read가 먼저 발생하면 평가를 실패시킨다.

## 3. Reference·Runtime schema

### 3.1 AlarmRef와 정규화

단일 fdc_alarm table은 만들지 않는다. 모든 알람 식별자는 다음 두 필드를 함께 가진다.

~~~text
AlarmRef
  source = TRACE | SUMMARY | R03
  alarm_id = non-empty string
~~~

URL token은 source와 alarm_id를 함께 encode한다. DB link, Agent State, Tool 입력, audit에도 두 값을
함께 저장한다. alarm_id 단독으로 source를 추측하지 않는다.

정규화된 AlarmEvidence는 다음을 가진다.

~~~text
alarm, occurred_at, area
equipment_id, chamber_id, parameter_id, recipe_id
lot_hist_id, lot_id, wafer_id, wafer_no, recipe_step_no
seq_no, alarm_type, rule_code, value, limit_type, limit_value, source_detail
~~~

`alarm_type`은 기존 `IN|OOC|OOS` 판정 Enum을 유지한다. R03는 `source=R03`,
`alarm_type=OOS`, `rule_code=R03_CONSEC`로 표현하며 `R03_CONSEC`를 AlarmType에 추가하지 않는다.
TRACE는 `rule_code=TRACE_OOS`, SUMMARY는 `rule_code=SUMMARY_OOC`를 사용한다.

### 3.2 R03 reference

r03_alarm_history는 final CSV가 아니라 evaluation으로부터 재생성하는 reference extension이다.

~~~text
group  = chamber_id, parameter_id, recipe_step_no
order  = chamber_wafer_cum ASC, track_in_at ASC, lot_hist_id ASC
scope  = LOT 경계를 넘어 연속성 유지
reset  = alarm_type != OOS
emit   = run이 3에 최초 도달한 행에서 1회
owner  = 세 번째 OOS의 lot_id·chamber_id
~~~

필수 컬럼은 alarm_id, occurred_at, lot_hist_id, lot_id, equipment_id, chamber_id, parameter_id,
recipe_step_no, trigger_wafer_no, member_wafer_refs, member_alarm_refs, policy_version이다.
`member_wafer_refs`는 연속 OOS의 `{lot_hist_id, wafer_id}` 정확히 3개이며,
`member_alarm_refs`는 그 세 WAFER·같은 parameter·step의 raw OOS TRACE AlarmRef 전체다. 최종
epoch에서는 R03 한 건당 9개다. WAFER ref는 계산 순서, AlarmRef는 해당 WAFER 순서 안에서
`seq_no ASC, alarm_id ASC`로 직렬화한다.

`policy_version`은 `R03_CONSEC_V1`이다. ID payload는 `source="R03"`, owner `lot_hist_id`,
`chamber_id`, `parameter_id`, 정수 `recipe_step_no`, `policy_version`을 key 오름차순·UTF-8·공백 없는 JSON으로
직렬화한다. SHA-256 앞 20개 lowercase hex에 `R03-`를 붙인다. occurred_at·member 배열은
provenance로 저장하되 ID payload에는 넣지 않아 정렬 표현 차이로 ID가 바뀌지 않게 한다.

최종 epoch 수용값은 R03 3건이다. 4번째 이상의 연속 OOS가 같은 run에서 중복 event를 만들면
실패한다.

### 3.3 기존 migration의 최종 DDL 호환성

001·002·003의 목적과 순서는 보존하지만 현재 파일을 최종 DDL에 즉시 적용하지 않는다.

| stage | 보존할 설계 의도 | 최종 전환 전 필수 검토 |

## 4. Detection·model 설계

### 4.1 Summary 재계산

그룹 key는 lot_hist_id, parameter_id, recipe_step_no다.

~~~text
value_mean = 산술평균
value_std  = 표본표준편차 ddof=1
value_min  = 최솟값
value_max  = 최댓값
point_cnt  = 점 개수
~~~

최종 summary_data 4,800행과 key·point count가 완전히 같고 수치는 0.001 이내여야 한다.

### 4.2 evaluation·TRACE alarm

dim_parameter를 한계선의 단일 출처로 사용한다.

1. raw value가 USL 또는 LSL을 벗어나면 OOS다.
2. OOS가 아니고 UCL 또는 LCL을 벗어나면 OOC다.
3. 그 외는 IN이다.
4. upper_only=true이면 하한을 판정하지 않는다.
5. step window에 OOS point가 하나라도 있으면 evaluation OOS, 아니면 OOC가 있으면 OOC, 그 외 IN이다.
6. OOS raw point마다 TRACE alarm 한 건을 만든다.

수용값은 evaluation IN 4,538·OOC 216·OOS 46, TRACE alarm 138이다.

### 4.3 SUMMARY alarm

관리한계 group은 chamber_id, parameter_id, recipe_step_no다.

1. evaluation이 OOS가 아닌 summary mean을 baseline 후보로 사용한다.
2. CL은 후보 평균, UCL·LCL은 CL ± 3 × sample standard deviation이다.
3. summary mean이 UCL 또는 LCL을 벗어나면 OOC alarm을 만든다.
4. occurred_at은 해당 wafer routing의 track_in_at이다.

수용값은 SUMMARY alarm 51건이며 occurred_at NULL은 0건이다.

### 4.4 anomaly score

anomaly score는 규칙 alarm을 대체하지 않고 wafer 이상 정도를 설명하는 보조 근거다.

- feature는 summary 통계, 한계선 상대 거리, point 이탈 비율, coverage를 사용한다.
- fault_code, metrology.alarm_result, Generator injection 상수, action_history는 feature에서 제외한다.
- split은 lot_id group 단위로 수행한다.
- 높은 값이 더 이상하도록 score 방향을 통일한다.
- normalization과 display threshold는 train LOT만으로 산정해 model manifest에 기록한다.
- score·threshold·is_anomaly는 nullable이며 artifact가 없어도 규칙 흐름은 정상 동작한다.
- 화면은 score, display threshold, model version을 표시할 수 있다.
- Agent는 score를 근거 문장에 인용할 수 있지만 조치 결정 근거와 구분한다.

기존 IncidentModelSignal, action threshold, score effect, score 기반 MONITORING→WARNING 상향,
활성 환경 gate는 최종 설계에서 사용하지 않는다. ActionPolicy signature에도 score를 넣지 않는다.

### 4.5 공개 합성 라벨 평가

평가는 Runtime 추론과 분리한 offline runner에서 수행한다.

~~~text
1. feature·model·prompt 입력을 구성한다.
2. prediction 결과와 code/model/dataset hash를 먼저 고정한다.
3. 평가 전용 role로 fault_code·metrology를 읽는다.
4. 고정 prediction과 label을 join한다.
5. synthetic 결과임을 명시한 metric artifact를 생성한다.
~~~

Fault 분류의 raw label은 6종이지만, alarm incident 원인 가설은 NRM을 제외한 5종으로 평가한다.
실측 12 incident 가운데 non-NRM member가 있는 TRACE incident 7건만 5-class 평가 대상으로
삼는다. SUMMARY-only incident 5건은 member label이 모두 NRM이므로 `NO_INJECTED_FAULT`로
제외·별도 보고하며 임의로 OTH 정답을 만들지 않는다. incident member에 서로 다른 비정상 label이
섞이면 임의 다수결하지 않고 `AMBIGUOUS_LABEL`로 제외·보고한다. 정상 NRM row는 anomaly
detection의 정상군 분석에 사용할 수 있으나 Agent의 예측 class로 넣지 않는다.

artifact에는 다음을 기록한다.

~~~text
public_fault_ground_truth_available = true
label_source = SYNTHETIC_GENERATOR
production_ground_truth_available = false
usage_scope = EVALUATION_ONLY
dataset_epoch, source hash, prediction hash
feature/model/prompt version, split manifest, metric
~~~

분류 accuracy와 class별 precision·recall·F1, metrology 기반 detection precision·recall을 계산할 수
있지만 실제 fab 성능 또는 production 품질로 표현하지 않는다. metrology는 48/600 lot_history
표본에만 존재하므로 metric artifact에 coverage 48/600을 기록하고 전체 데이터로 외삽하지 않는다.
공개 label로 후보 model·feature·normalization·threshold를 선택한 뒤 같은 row에서 성능을
보고하지 않는다. 후보는 라벨을 읽기 전에 고정하고 synthetic holdout 결과는 같은 revision의
재튜닝에 사용하지 않는다.

### 5.2 안전 적재

원본 master.cypher 첫 문장의 MATCH (n) DETACH DELETE n은 공용 Neo4j에서 실행하지 않는다.

1. loader가 destructive statement와 seed statement를 분리한다.
2. 기본 모드는 empty graph만 허용한다.
3. populated 교체는 기존 fingerprint, 팀 공유, backup·restore 검증, replace와 confirm을 요구한다.
4. seed를 transaction으로 적용하고 label·business key·relationship type을 검증한다.
5. node 44·relationship 85와 중복 business key 0을 확인한다.
6. 성공 후에만 epoch·source hash·graph fingerprint marker를 원자적으로 기록한다.

relationship에는 방향·type·business endpoint의 canonical tuple로 만든 stable relation ID를
부여한다. 알고리즘 이름은 `REL-SHA20`이며 tuple은
`<TYPE>|<FROM_LABEL>:<FROM_BUSINESS_ID>|<TO_LABEL>:<TO_BUSINESS_ID>`다. business ID는
`bk-v1`의 key 오름차순 `key=s:<NFC-value>`(정수는 `key=i:<decimal>`) 직렬화이고 tuple의 UTF-8
SHA-256 앞 20 lowercase hex에 `REL-`을 붙인다. 예:
`MEASURED_ON|Parameter:parameter_id=s:PH_FOCUS|Chamber:chamber_id=s:EQP01-PM1`
→ `REL-9687560b5876022b2512`. Neo4j elementId는 API provenance로 사용하지 않는다.

`graph_revision`은 source hash나 marker file hash가 아니라 성공 marker의
`actual_graph_fingerprint_sha256` 64 lowercase hex다. marker는 dataset epoch
`fdc_final_20260818`, source member SHA-256
`51604707c9a0f3bc97b21773b7bd43d0049f2dacf322042c36f090ec63c74eea`, 44/85,
`expected_graph_fingerprint_sha256 == actual_graph_fingerprint_sha256`를 만족하고 live graph를
같은 canonical 알고리즘으로 다시 계산한 fingerprint도 actual과 같을 때만 유효하다. 최종 graph의
기대 fingerprint는 `3474debee491ea5c699080109d748a4922ad0566a3b84568e9067053de2fa2eb`다.
marker는 graph transaction commit과 live 검증이 끝난 뒤 마지막으로 원자 기록한다.

정상에 따른 하향 문구는 제거한다. metrology·LLM·predicted fault·anomaly score는 조치 근거를
설명할 수 있을 뿐 3단계 규칙 결과를 바꾸지 못한다. raw 한 점의 USL/LSL 이탈은 즉시 TRACE
알람이라는 R01 설명으로 모순 문구를 정정하고 Fault 후보에는 `OTH`를 포함한다.
PH 문서는 PH-9000 모델 범위를 EQP01~03·RECIPE01/03으로, ET 문서는 ET-7500 범위를
EQP04~06·RECIPE02/04로 본문 자체에서 정정해 chunk마다 대표 설비를 전체 범위로 오해하지 않게 한다.

①의 `load_documents.py`는 그대로 실행하지 않고 다음 adapter 계약을 적용해 재사용한다.

1. 입력 경로는 ③ 원문이 아니라 검증된 정정본 3종의 명시적 경로만 받는다.
2. DSN과 target database는 필수 인자다. database allowlist, expected schema, 쓰기 권한을
   preflight하고 로컬 기본 DSN·암묵적 fallback을 금지한다.
3. chunk ID는 `<document_id>:<chunk_schema_version>:<4자리 순번>`으로 생성한다.
4. 세 문서의 기존 동일 ID row 정리, document·chunk·embedding 저장은 한 transaction에서
   수행한다. 중간 실패 시 전부 rollback한다.
5. 같은 source·corrected hash와 chunk ID를 재적재하면 중복 없이 같은 row·hash가 남아야 한다.
6. `--reset`과 `DELETE FROM document[_chunk]` 전체 삭제는 금지한다. 교체 transaction은 위 세
   canonical `doc_id`에 해당하는 row만 삭제·재삽입하며 다른 문서는 건드리지 않는다.
7. `model_code` filter가 있으면 `d.model_code = :model_code OR d.model_code = 'COMMON'`을
   적용한다. filter가 없으면 세 문서 전체가 검색 대상이다.

원문 YAML의 `DOC-SPEC-PH9000`, `DOC-SPEC-ET7500`, `DOC-TROUBLE-FDC`를 canonical
`document_id`로 승계한다. 정정본이 임의의 별칭으로 바꾸지 않으며, `chunk_id`는
`<document_id>:<chunk_schema_version>:<4자리 순번>`으로 결정론적으로 생성한다. 최초
`chunk_schema_version`은 `cs2`이고 다음 규칙을 정확히 적용한다.

1. UTF-8로 읽고 CRLF/CR을 LF로, Unicode를 NFC로 정규화한 뒤 YAML front matter를 분리한다.
2. H2 heading은 독립 주제 section으로 사용한다. 첫 H2 전 본문은 첫 H2 content 앞에 붙인다.
   H3 heading은 상위 H2 제목을 `<H2> > <H3>` 형식으로 포함한 독립 section으로 사용한다.
3. section content가 1,000자를 넘으면 빈 줄 문단을 순서대로 greedy 분할한다. 단일 문단 자체가
   1,000자를 넘으면 그 문단은 추가 문자 단위 분할 없이 보존한다.
4. 두 번째 이후 조각의 section은 `<원 section> (<1-based 조각 번호>)`다.
5. 짧은 조각도 다른 section과 병합하지 않는다.
6. semantic split이 끝난 뒤 1부터 순번을 부여하고 4자리 zero-pad한다. 저장 content에는 title을 넣지 않고,
   embedding 입력만 `<document title> / <section>\n\n<content>`로 만든다.
7. `normalize_embeddings=True`를 사용한다.

hash 입력 JSON은 다음 한 줄과 정확히 같다.

```json
{"chunk_id_format":"<document_id>:cs2:<seq:04d>","continuation_title_format":"<section> (<piece_index_1_based>)","contract":"rag-chunk-cs2","decode":"utf-8","embedding_input_format":"<document_title> / <section>\n\n<content>","fallback_section_title":"문서 안내","h2_body_handling":"emit-only-when-nonempty","h2_heading_regex":"^##\\s+(.+?)\\s*$","h3_heading_regex":"^###\\s+(.+?)\\s*$","heading_hierarchy":"H2-topic;H3-independent-child-with-H2-title-context","line_endings":"LF","long_section_split":"blank-line-paragraph-greedy;oversize-paragraph-unsplit","max_chars":1000,"normalization":"NFC","preamble_handling":"prepend-to-first-H2","sequence":"1-based-after-semantic-split","short_piece_merge":"none","version":2}
```

위 JSON을 key 오름차순·UTF-8·공백 없는 형태 그대로 직렬화한
`chunk_contract_sha256`은
`1b6571df8a8c3fdcd4de8f7f7184340273184ea72b14b3dbc1ee6e1b8c7f266b`다. 규칙이 하나라도
바뀌면 `cs2`나 이 hash를 재사용하지 않는다. 임베딩은
`BAAI/bge-m3` revision `5617a9f61b028005a4858fdac845db406aefb181`로 고정하고
`pytorch_model.bin` SHA-256
`b5e0ce3470abf5ef3831aa1bd5553b486803e83251590ab7ff35a117cf6aad38`와 dimension 1024를
preflight한다. branch `main` 또는 revision 생략은 허용하지 않는다.

적재는 위 2.4 matrix의 세 DB 모두에 같은 schema와 corrected canonical 문서 3종을 적용한다.
각 DB transaction commit 뒤 live row를 다시 읽어 검증한 다음에만 marker를 마지막으로 원자
기록한다. marker JSON은 최소 다음 field를 갖는다.

~~~text
format_version=1, artifact_type=rag_load_marker, status=COMMITTED
dataset_epoch, database, schema_sha256
document_ids[3], source_sha256_by_document, corrected_sha256_by_document
chunk_schema_version=cs2, chunk_contract_sha256
embedding_model, embedding_model_revision, embedding_weights_sha256, dimension=1024
document_count=3, chunk_count, null_embedding_count=0
live_db_fingerprint_sha256, search_smoke[3]
~~~

`live_db_fingerprint_sha256`는 document를 `doc_id ASC`, chunk를
`doc_id ASC, chunk_seq ASC, chunk_id ASC`로 읽어 vector 자체를 제외한 canonical scalar
row(`doc_id/title/doc_type/model_code/source_path/version`,
`chunk_id/doc_id/chunk_seq/section_title/content/token_cnt/metadata_json`)와 위 chunk/model metadata를
NFC·key 정렬·공백 없는 JSON으로 hash한 값이다. vector는 별도로 NULL 0·dimension 1024를
검사한다. marker가 없거나 COMMITTED가 아니거나 live fingerprint가 다르면 적재 성공으로 보지
않는다.

검색 smoke는 모두 `top_k=4`로 실행하며 (1) `PH-9000 Photo Scanner 적용 범위` +
`model_code=PH-9000` → `DOC-SPEC-PH9000`, (2) `ET-7500 Dry Etcher 적용 범위` +
`model_code=ET-7500` → `DOC-SPEC-ET7500`, (3) `연속 3 WAFER OOS 승인 조치` +
`model_code=PH-9000` → `DOC-TROUBLE-FDC`가 각각 top-4에 있어야 한다. 세 번째는 `COMMON`
포함 filter도 함께 검증한다. readiness는 runtime `kosa_agent` marker와 live DB만 검사하고 E2E·
evaluation marker는 각 전용 검증 command가 확인한다. API provenance는 안정적인
`document_id`·`chunk_id`를 반환하며 RAG 단위 version 문자열을 만들지 않는다.

get_equipment_context는 graph의 구조와 relation_id를 반환하고 특정 LOT의 실제 upstream equipment를
합성하지 않는다.

## 6. LangGraph Agent

### 6.1 incident

incident key는 lot_id와 chamber_id의 쌍이다. TRACE·SUMMARY·R03 AlarmRef가 하나 이상인 key만
생성한다. 최종 데이터에서는 12개다.

- 대표 AlarmRef는 occurred_at ASC, source priority, alarm_id ASC의 첫 행이다.
- source priority는 R03, TRACE, SUMMARY 순이며 대표 선택 안정성만 위한 값이다.
- 모든 member AlarmRef를 agent_run_alarm에 저장한다.
- evaluation DB의 action reference 12건을 Runtime incident seed나 Agent 정답으로 사용하지 않는다.
- 자동 실행은 Runtime action이 없는 incident만 선택한다.

load_incident는 member를 resolve하고 wafer_id별 lot_history를 track_in_at 순으로 조회한다.
Neo4j ProcessStep 구조와 cross-check하되 실제 routing의 기준은 PostgreSQL이다.

### 6.2 State

State는 다음을 가진다.

~~~text
run_id, thread_id, retry_of_run_id
requested_alarm, representative_alarm, member_alarms
lot_id, chamber_id, route
fdc_evidence, optional_anomaly_evidence
graph_evidence, document_evidence
hypothesis, action_decision
action_id, approval_id, deliveries
tool_budget, errors
~~~

optional_anomaly_evidence는 score·display threshold·model version·is_anomaly를 담지만
action_decision의 입력이 아니다. State·checkpoint에는 fault_code label, Generator injection 정보,
비밀번호·API key·전체 DSN을 저장하지 않는다.

### 6.3 그래프

~~~mermaid
flowchart TD
    S[load incident and route] --> F[get_fdc_summary]
    F --> G[get_equipment_context]
    G --> R[search_documents]
    R --> H[generate_hypothesis]
    H --> D[decide_action by alarm rules]
    D --> P[persist action and delivery plan]
    P -->|MONITORING| Z[finalize]
    P -->|WARNING| E[n8n SMTP]
    E --> Z
    P -->|EQP_HOLD| N[n8n approval email]
    N --> I[HITL interrupt]
    I -->|APPROVED| K[n8n publish fdc.actions]
    I -->|REJECTED| X[cancel MES delivery]
    K --> W[n8n consume fdc.actions.result and write-back]
    W --> Z
    X --> Z
~~~

### 6.4 원인 가설

구조화 출력은 predicted_fault_code, confidence, cause_summary, supporting AlarmRef·chunk_id·
relation_id, uncertainty를 포함한다.

- predicted_fault_code는 FOC·RFM·MFD·TMD·OTH 중 하나다.
- NRM은 이미 alarm이 발생한 incident의 원인 가설 class가 아니다.
- fault_code label과 Generator FAULTS는 prompt에 넣지 않는다.
- confidence는 LLM 자기보고이며 교정 확률로 표현하지 않는다.
- 구조 검증 실패 시 교정 요청은 최대 1회다.
- 인용 ID는 같은 run의 Tool 결과에 실제 존재해야 한다.

LLM provider·model은 참고 구현 기준(`backend/agent/agent_graph.py`의 `ChatAnthropic`,
`MODEL=claude-sonnet-4-5`)을 출발점으로 하고 환경변수로 교체 가능하게 둔다. API 자격증명은
멘토님이 지원한다. key·전체 DSN은 State·checkpoint·로그·artifact에 저장하지 않는다.

### 6.5 조치 결정

ActionPolicy.decide(IncidentSignal) 함수는 DB·LLM·model score·network를 사용하지 않는다.

| 우선순위 | 조건 | action | severity | 승인 |
|---:|---|---|---|---|
| 1 | R03 존재 | EQP_HOLD | HIGH | 사람 |
| 2 | R03 없음, TRACE OOS 존재 | WARNING | MEDIUM | 자동 |
| 3 | SUMMARY OOC만 존재 | MONITORING | LOW | 자동 |
| - | 실제 alarm 없음 | action 없음 | 없음 | 없음 |

여러 신호가 있으면 가장 높은 한 건만 생성한다. raw OOS point 수만으로 R03를 추정하지 않는다.
predicted fault, LLM confidence, anomaly score, metrology PASS/FAIL은 action 입력에서 제외한다.

final epoch의 reference 분포 MONITORING 5·WARNING 4·EQP_HOLD 3은 규칙 회귀 fixture다.
Runtime Agent는 reference action row를 복사하지 않고 같은 alarm 입력에서 직접 결정한다.

## 7. Action·HITL·자동화

### 7.1 생성 transaction

| action | approval_status | delivery 초기 상태 |
|---|---|---|
| MONITORING | AUTO | 없음 |
| WARNING | AUTO | EMAIL=WAITING |
| EQP_HOLD | PENDING | EMAIL=WAITING, MES_MOCK=BLOCKED |

action_history, agent_run_action, approval_request, action_delivery를 한 transaction에서 만든다.
incident lock 안에서 기존 CREATED action을 다시 조회하고 중복이면 재사용하거나 409로 처리한다.

### 7.2 승인

~~~text
APPROVED
  approval_request PENDING → APPROVED
  action_history approval_status → APPROVED
  MES_MOCK BLOCKED → WAITING
  commit
  동일 run/thread 재개
  Kafka publish

REJECTED
  approval_request PENDING → REJECTED
  action_history approval_status → REJECTED
  MES_MOCK BLOCKED → CANCELED
  commit
  외부 MES 효과 없음
~~~

결정 요청은 APPROVED·REJECTED만 받는다. 같은 승인에 대한 재결정은 409다.

### 7.3 n8n SMTP

WARNING과 EQP_HOLD 이메일은 Backend가 서명된 webhook으로 n8n을 호출하고 n8n이 실제 SMTP로
발송한다.

- payload에는 action_id, channel, request_hash, 수신자, 조치·설비·근거의 최소 필드만 넣는다.
- Backend→n8n과 n8n→Backend 모두 `X-Delivery-Timestamp`와 `X-Delivery-Signature`를 사용한다.
  signature는 `N8N_WEBHOOK_SECRET`으로 `timestamp + "." + raw_body`를 HMAC-SHA256한
  `sha256=<64 lowercase hex>`이며 raw bytes·constant-time 비교·300초 replay window를 적용한다.
- `request_hash`는 `sha256:<64 lowercase hex>`이고 n8n이 재계산·변경하지 않고 callback과 Kafka
  result까지 그대로 전달한다. `(action_id, channel, request_hash)`로 중복 효과를 억제한다.
- 발송 성공·실패 callback은 같은 action_id·channel·hash를 포함한다.
- EQP_HOLD 이메일은 승인 요청을 알리지만 MES 실행 성공을 뜻하지 않는다.
- MONITORING에는 이메일 delivery를 만들지 않는다.

**workflow는 팀 산출물이다.** 최종 패키지에는 import 가능한 n8n workflow JSON이 없고
`docs/07_n8n_워크플로_제작가이드.md` §8이 화면에서 만든 뒤 저장소에 커밋하도록 지정한다.

~~~text
deploy/n8n/WF2-notify-email.json        담당자 이메일 통지 (SMTP 실발송)
deploy/n8n/WF3-mes-hold.json            승인 후 MES 설비 홀드 (Kafka)
deploy/n8n/WF4-result-writeback.json    결과 write-back (Kafka Trigger)
~~~

최종 참고의 `WF1-alarm-to-agent`는 단수형 stale `POST /agent/run`을 전제로 하므로 팀 필수
workflow에서 제외한다. Agent 실행 진입점은 Alarm 화면의 source-aware `POST /agent/runs`다.
n8n은 학원 제공 외부 공용 canonical 서비스로 연결하고 팀 compose에 두 번째 n8n을 추가하지
않는다.

### 7.4 Kafka MES Mock

Kafka MES Mock은 **필수 범위**이며 C가 소유한다. broker의 **운영 위치(공용 서버 1벌 / 팀원
로컬)만 미정**이고 compose 통합 시 확정한다. 공용 broker를 쓸 경우 팀 간 `fdc.actions` 토픽
충돌을 막는 규칙을 함께 정한다.

승인된 EQP_HOLD만 Backend가 n8n의 fdc-mes-hold webhook을 호출하고, n8n Kafka Producer가
topic fdc.actions에 JSON event를 발행한다.

`request_hash`는 전송 시각·서명·request_hash 자체를 제외한 immutable delivery request
(`action_id`, 내부 `channel`, action·설비·명령, EMAIL이면 recipient·template ID)를 NFC,
key 오름차순, 공백 없는 JSON으로 직렬화한 UTF-8 SHA-256이다. 같은 action/channel retry는 같은
hash를 재사용하고 payload 의미가 달라져 hash가 바뀌면 멱등 충돌로 거부한다.

~~~text
Kafka record key = action_id
payload:
  event_id, action_id, action_code
  equipment_id, chamber_id, command=HOLD
  decided_by, decided_at
  request_hash, occurred_at
~~~

MES Mock consumer는 입력 payload의 `action_id`와 `request_hash`를 보존해 처리 결과를
`fdc.actions.result`에 발행한다. result record key도 `action_id`다. n8n Kafka Trigger가 결과를
소비해 `POST /internal/actions/{action_id}/delivery`로 변환하여 write-back한다. Kafka result의
`action_id`는 endpoint path에 넣고, 결과 channel은 `MES_MOCK`으로 정규화한다. SMTP callback도
같은 endpoint를 사용하되 channel은 `EMAIL`이다.

internal callback은 `X-Delivery-Timestamp`와 `X-Delivery-Signature`를 사용한다. signature는
`N8N_WEBHOOK_SECRET`으로 `timestamp + "." + raw_body`를 HMAC-SHA256한 `sha256=<hex>`이며
constant-time 비교와 300초 replay window를 적용한다. body를 JSON으로 다시 직렬화한 값이 아니라
수신한 raw bytes를 검증한다.

~~~text
path: action_id
body:
  event_id, channel=EMAIL|MES_MOCK, status=SENT|FAILED
  provider_message_id, request_hash
  completed_at, error_code

DeliveryResult:
  action_id, channel, status, request_hash
  provider_message_id, completed_at, error_code
  duplicate: boolean
~~~

transport는 at-least-once로 보고 n8n workflow와 MES Mock consumer가 action_id·request_hash를
멱등 key로 사용한다.
같은 hash 재수신은 외부 효과를 반복하지 않고 같은 결과를 재발행한다. 같은 action_id의 다른 hash는
충돌로 거부한다. n8n result workflow는 action_delivery를 SENT 또는 FAILED로 write-back한다.

제공 produce_test.py와 result_writeback.py는 n8n 없이 topic 흐름을 확인하는 개발 smoke
대체물이다. 최종 통합 경로의 상태 기준으로 사용하지 않는다.

승인 전 publish, REJECTED·CANCELED publish, SENT 자동 재발행은 금지한다. 결과를 알 수 없는 timeout은
UNKNOWN으로 두고 운영자 확인 없이 자동 재발행하지 않는다.

### 7.5 delivery 상태

~~~text
BLOCKED → WAITING
WAITING → SENDING
SENDING → SENT | FAILED | UNKNOWN
BLOCKED → CANCELED
FAILED → WAITING    명시적 retry만
~~~

멱등 기준은 action_id·channel이며 channel은 EMAIL·MES_MOCK이다. transport metadata로
N8N_WEBHOOK 또는 KAFKA, topic·partition·offset·provider ID를 result에 기록할 수 있다.

## 8. Tool 계약

모든 Tool 반환은 `ok`, `reason`, 도구별 domain payload만 유지한다. 성공이면 reason은 빈 문자열,
실패이면 허용된 오류 prefix를 사용하고 payload field는 null 또는 빈 목록이어야 한다.
`latency_ms`와 호출 status는 Tool payload가 아니다. 공통 wrapper가 호출 시작을 예약하고 종료 시
같은 `agent_tool_call` 한 행에 input/output, `SUCCESS|ERROR|TIMEOUT`, `latency_ms`를 정확히 한 번
갱신한다. Tool 구현과 LangGraph node가 이를 중복 기록하지 않는다.

허용 reason prefix는 아래 일곱 종뿐이다.

```text
NOT_FOUND:  TIMEOUT:  MODEL_NOT_READY:  LLM_NOT_READY:
DEPENDENCY_ERROR:  POLICY_REJECTED:  IDEMPOTENCY_CONFLICT:
```

| Tool | 입력 | 결과 요점 |
|---|---|---|
| `get_fdc_summary(lot_hist_id)` | `lot_hist_id` | summary·evaluation·한계선·선택적 anomaly evidence. fault label 제외 |
| `get_equipment_context(chamber_id)` | `chamber_id` | graph node·relation provenance와 ProcessStep adjacency |
| `search_documents(query, model_code=None, top_k=4)` | query, optional model, 1..10 | 검증된 corrected RAG source의 DocumentHit. model filter는 COMMON 포함 |
| `send_action(action_id)` | `action_id` | 저장된 plan·승인 상태에 따른 채널별 status·sent·duplicate |
| `generate_analysis_plan(question)` | `question` | 선택 Analytics 확장의 SQL·metric·chart plan |

send_action은 action 결정을 하지 않고 저장된 delivery plan과 승인 상태를 검증해 adapter를 호출한다.
호출자가 channel·agent_run_id를 넘기지 않는다. MES_MOCK은 승인되지 않으면 POLICY_REJECTED로
실패한다. get_fdc_summary의 anomaly_score가 있어도
조치 권고를 반환하지 않는다.

### 9.3 기존 route·API 확장

현재 React·Backend의 다음 기능은 필수 5개 화면을 깨지 않는 선택 확장으로 유지할 수 있다.

- /dataset/bounds와 /dashboard/summary server aggregation
- source-qualified alarm detail과 /traces 상세
- /actions, /agent/runs/{run_id}, 별도 /approvals·/audit-logs route
- /relations legacy route
- /analytics와 Text2SQL
- 평가 이력·내부 delivery retry·readiness

현재 저장소 React는 최종 package snapshot과 달리 7개 메뉴·기존 route를 유지한다. 이를 완료
상태로 보지 않고 WBS v5에 5개 메뉴 전환, 9개 호환 API projection, Ontology 보안 API 소비,
감사 wrapper 실제 화면 연결을 필수 adapter Task로 둔다.

기존 /dashboard, /relations, /knowledge, /approvals, /audit-logs URL은 redirect 또는 tab adapter로
보존한다.
필수 메뉴 수를 늘리지는 않는다. Text2SQL은 최종 5개 화면의 완료 조건이 아니며 구현되어 있으면
선택 확장으로 격리한다.

### 9.4 Naming adapter

물리 CSV는 equipment, chamber, parameter, recipe, lot, wafer를 사용하지만 서비스 내부 canonical
DTO는 equipment_id, chamber_id, parameter_id, recipe_id, lot_id, wafer_id를 사용한다.
Repository mapper 한 곳에서 물리 column을 canonical field로 변환한다. deprecated React alias는
단일 API boundary compatibility serializer만 canonical 값에서 파생할 수 있으며 Router handler·
Service·Repository가 각자 alias 규칙을 재구현하거나 DB label column을 직접 읽어 만들지 않는다.

area canonical 값은 Photo·Etch·ALL이다. 기존 lowercase photo·etch query는 호환 adapter가
정규화할 수 있지만 응답은 canonical case를 사용한다.

### 9.5 조회·정렬

GET /alarms의 date_from, date_to, area, equipment, chamber, parameter, source,
include_derived는 선택이다. 실제 최종 Frontend가 mount 시 무파라미터 호출하므로 생략하면 final
epoch 전체 기간·ALL을 적용한다. 날짜는 둘 다 주거나 둘 다 생략하며 한쪽만 주면 422다.

- alarm: occurred_at DESC, source ASC, alarm_id DESC
- run/action/approval: created_at DESC, ID DESC
- audit: occurred_at DESC, audit_id DESC
- page는 1 이상, size는 1~100
- 날짜 경계는 Asia/Seoul

최종 CSV의 offset 없는 timestamp는 Asia/Seoul local time으로 해석해 적재하고, API에서는
`+09:00` offset을 포함한 ISO 8601 `date-time`으로 직렬화한다. offset 없는 API timestamp를
새로 만들지 않는다.

빈 결과라도 요청의 date range를 유지하고 목록·집계만 비운다. source data 자체가 없어 bounds를
만들 수 없으면 Empty가 아니라 readiness 실패다.

## 10. 선택 Analytics

Text2SQL은 5개 필수 화면 밖의 선택 확장이다. 유지할 경우 runtime readonly pool과 evaluation

`POST /agent/ask` 경계: Agent Chat mode의 PostgreSQL 근거 조회는 Agent Tool의 고정·파라미터화된 조회를 사용하며, 본 절의 자연어 Text2SQL 변환·실행 경로를 호출하지 않는다. 필수 기능인 `/agent/ask`가 선택 확장인 본 절 경로에 의존하지 않게 하기 위함이다. 1. 단일 SQL statement
2. SELECT 계열만 허용
3. allowlist table·view·column
4. system catalog·위험 함수 차단
5. recursive CTE·subquery 재검사
6. LIMIT 500
7. readonly transaction·statement timeout
8. fault_code는 일반 사용자 query allowlist에서 제외

## 12. 동시성·Checkpoint·복구

### 12.1 동시성

incident 실행과 action 생성은 lot_id·chamber_id advisory lock, transaction 재조회,
부분 고유 index로 방어한다.

- RUNNING·WAITING_APPROVAL 동시 실행은 409다.
- COMPLETED incident 재실행은 기본 409다.
- FAILED만 명시적 retry를 허용한다.
- action 생성 후 retry는 기존 action을 REUSED로 연결한다.
- Kafka·SMTP retry는 새 action을 만들지 않는다.

### 12.2 Checkpoint

PostgresSaver setup은 admin command로만 실행한다. 앱 시작 시 DDL을 자동 수행하지 않는다.
interrupt 전에 action·approval·Tool budget을 commit하고 thread_id를 agent_run에 저장한다.

### 12.3 복구

| 장애 | 처리 |
|---|---|
| stale RUNNING + checkpoint | 같은 run·thread 재개 |
| checkpoint 없음 + action 존재 | DB 상태로 복구, 새 action 금지 |
| 승인 commit 후 재개 실패 | 승인 run 재개 command |
| SMTP callback 유실 | provider 확인 후 SENT·FAILED·UNKNOWN |
| Kafka result 지연 | SENDING 유지 후 timeout 시 UNKNOWN, 자동 republish 금지 |
| 명시적 FAILED retry | 같은 action_id·channel·request_hash 사용 |

reset은 Runtime·checkpoint table만 대상으로 한다. 9개 base table, R03, RAG document table,
evaluation snapshot은 삭제하지 않는다.

## 13. 배포·보안·readiness

### 13.1 공용 서버

- PostgreSQL·Neo4j·n8n은 팀 공용 서버를 사용한다.
- 세 서비스의 외부 공용 endpoint가 canonical이다. 팀 compose는 Backend·Frontend·Kafka·
  MES Mock만 기동하며 PostgreSQL·Neo4j·n8n 서비스 정의·volume·기본 credential을 추가하지 않는다.
- database 생성·schema 초기화·migration·전체 graph 교체 전 대상과 시간을 공유한다.
- source ZIP의 docker default credential을 공용 환경에 복사하지 않는다.
- application, readonly, evaluation, query-log, bootstrap role을 분리한다.
- 공용 graph에 raw master.cypher를 직접 실행하지 않는다.
- CORS는 명시 Origin allowlist를 사용한다.
- Kafka broker credential과 n8n webhook secret을 환경변수로 주입하고 log에 남기지 않는다.

### 13.2 readiness

`/health`는 process 생존만 검사하고 200 `HealthResponse`를 반환한다.

~~~text
HealthResponse
  status: "UP"
~~~

`/health/ready`는 다음을 병렬·timeout으로 검사한다.

- `postgresql_runtime`: runtime profile epoch·schema·권한
- `reference_migration`: compatibility marker
- `neo4j`: 44/85 success marker와 fingerprint
- `rag`: runtime `kosa_agent`만 대상으로 `document`·`document_chunk` schema, canonical document
  ID 3종, source·corrected SHA-256, cs2 contract hash, 고정 model revision·weights hash,
  COMMITTED marker와 live DB fingerprint, chunk 1건 이상/문서, NULL embedding 0건,
  vector dimension 1024, 지정 검색 smoke 3건
- `n8n`: webhook·workflow readiness
- `kafka`: metadata와 `fdc.actions`·`fdc.actions.result` topic 접근

~~~text
ReadinessCheck
  status: PASS | FAIL
  reason_code: string | null
  latency_ms: integer >= 0

ReadinessResponse
  status: READY | NOT_READY
  dataset_epoch: fdc_final_20260818
  checks: {
    postgresql_runtime, reference_migration, neo4j, rag, n8n, kafka
  }
~~~

모든 check가 PASS면 200과 `status=READY`, 하나라도 FAIL이면 같은 DTO를 담은 503과
`status=NOT_READY`를 반환한다. anomaly model은 action 규칙의 필수 dependency가 아니다.
model artifact가 없어도 Detection rule·Agent action readiness는 실패하지 않는다.
`reason_code`는 allowlist된 code만 사용하고 host·port·계정·secret·
원본 exception을 노출하지 않는다.

11. Kafka result 유실은 UNKNOWN, 자동 republish 0.
12. Tool·dependency timeout에서 budget·state·audit 일관성 유지.

### 14.4 평가 경계

- 공개 합성 label을 이용한 metric에는 Synthetic Generator Dataset 표기를 붙인다.
- production_ground_truth_available=false를 항상 기록한다.
- prediction을 고정하기 전 label table을 읽으면 평가 runner가 실패한다.
- Agent evidence AlarmRef·chunk_id·relation_id 유효율은 100%여야 한다.
- action code는 anomaly score를 바꿔도 규칙 입력이 같으면 100% 일치해야 한다.
- RAG에는 고정 EQP upstream 문구가 없어야 한다.
- graph API가 반환한 relation_id는 검증 marker가 가리키는 현재 graph에 실재해야 한다.
