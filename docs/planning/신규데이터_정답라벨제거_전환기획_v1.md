# BISTel FDC 프로젝트 신규 데이터 전환 기획

## 1. 개정 목적

멘토님께서 새로 제공하신 `kosa_0813.zip`은 기존 배포 자료와 달리 공개 Fault 정답 라벨을 제공하지 않는 데이터셋이다. 이에 따라 기존 기획의 `fault_code` 기반 학습·평가, 고정 Fault 분류 정답, 기존 알람·조치 ID 기반 수용 기준을 폐기하고 다음 원칙으로 프로젝트를 재정의한다.

- 규칙으로 계산 가능한 값은 결정론적 계산 결과로 검증한다.
- Fault 원인과 이상 여부를 공개 라벨이 있는 것처럼 평가하지 않는다.
- 비지도 이상감지 모델은 규칙 조치를 대체하지 않으며, 검증된 모델·threshold가 활성화된 경우에만
  `MONITORING`을 `WARNING`으로 한 단계 상향하는 보조 신호로 사용한다. 모델 점수만으로
  `EQP_HOLD`·HITL 또는 신규 incident를 만들지 않는다. `[팀 잠정]`
- Agent의 원인 분류는 `정답 분류`가 아니라 근거가 포함된 `원인 가설`로 취급한다.
- 조치·승인·전송은 업무 규칙, 상태 전이, 멱등성으로 검증한다.
- 기존 자료와 신규 자료가 충돌하면 신규 자료를 기준으로 하되, 불명확한 정책은 코드에서 분리하고 `[팀 잠정]`으로 관리한다.

> **평가 전제.** 신규 자료의 `summary_data`, `evaluation`, `trace_alarm_history`, `summary_alarm_history`는 원천 `fdc_trace`로부터의 결정론적 재현 기준을 제공한다. 반면 `lot_history.fault_code`는 전 행이 `NRM`인 placeholder이며 FOC·RFM·MFD·TMD·OTH 분류의 공개 정답 라벨로 사용하지 않는다. `metrology`의 PASS/FAIL은 제품 계측 결과이며 Fault Mode 정답과 구분한다. 따라서 Detection 재현은 reference output과 정량 비교하되, 제공 라벨을 사용한 실제 데이터 성능은 주장하지 않는다. 팀이 원본과 분리해 만든 합성 평가셋은 `label_source=SYNTHETIC_GENERATOR`로만 평가하며 실제 공정 Accuracy·Precision·Recall·F1과 구분한다. 별도 전문가 라벨셋이 확정될 때만 실제 데이터 분류 지표를 추가한다.

## 2. 문서 내 상태 표기

| 표기 | 의미 | 개발 처리 |
|---|---|---|
| `[자료 확정]` | 신규 ZIP의 DDL·CSV·가이드와 실측 결과가 일치하는 사실 | 즉시 구현 가능 |
| `[팀 잠정]` | 개발을 멈추지 않기 위해 팀이 정한 가역적 정책 | 설정·함수·어댑터로 분리하여 구현 |
| `[멘토 확인]` | 자료 간 충돌 또는 공식 기준이 없는 정책 | 외부 인터페이스를 고정하지 않고 답변 후 교체 |

기존 요구사항정의서·시스템설계서·역할분담·WBS는 본 기획을 반영한 차기 버전이 확정될 때까지 참고 자료로만 사용한다. 특히 기존 데이터의 고정 건수, ID, Fault 정답과 조치 정답은 신규 개발의 기준값으로 사용하지 않는다.

## 3. 신규 데이터 기준선

### 3.1 원본 기준

| 항목 | 신규 기준 | 사용 원칙 |
|---|---:|---|
| `lot_history` | 600행 | `fault_code`는 공개 정답 라벨로 사용하지 않음 |
| `fdc_trace` | 14,400행 | 보정 후 원시 시계열 입력으로 사용 |
| `summary_data` | 4,800행 | Trace 재계산 대상 |
| `evaluation` | 4,800행 | 제공 파생값이며 모델 성능 Gold가 아님 |
| `trace_alarm_history` | 126행 | 제공 파생 fixture, 규칙 비교 참고용 |
| `summary_alarm_history` | 47행 | `occurred_at` 보정 필요 |
| `metrology` | 48행 | PASS 39·FAIL 9, 결과 근거이며 Fault 정답이 아님 |
| `action_history` | 48행 | 화면 Mock/reference로만 보존, Agent runtime seed에서 제외 |
| Neo4j | 38 nodes·81 relationships | `master.cypher` 구조 검증 |

위 건수는 신규 원본과 제공 파생 파일의 구조를 확인하기 위한 기준이다. 모델 Accuracy·Precision·Recall·F1을 주장하는 정답 건수가 아니다.

### 3.2 원본 보존과 보정 데이터

- `[자료 확정]` `kosa_0813.zip`을 유일한 신규 source baseline으로 둔다.
- `[자료 확정]` 기존 `1785496094907.zip`은 historical 비교용으로 격리하며 신규 CSV를 대신하지 않는다.
- 신규 ZIP SHA-256은 `8bbe0bdd646290e2da300db0c293d6775927f61a35375721d4b042b239803c96`이다.
- 원본 ZIP과 압축 해제본은 수정하지 않고 SHA-256 manifest를 남긴다.
- 보정은 별도 스크립트가 corrected copy를 생성하는 방식으로 수행한다.
- 보정 전후 행 수·컬럼·해시·적용 규칙을 manifest와 검증 보고서에 기록한다.

### 3.3 개발 진행을 위한 데이터 보정 정책

| 항목 | 현재 문제 | 진행 정책 |
|---|---|---|
| `dim_parameter` | DDL에 테이블만 있고 seed가 없어 Trace FK 적재가 불가능 | `[팀 잠정]` 신규 Generator의 parameter 사양과 기존 자료의 단위 정보를 대조해 8행 seed overlay 생성. 멘토 정정본 수신 시 교체 |
| `fdc_trace.seq_no` | Recipe Step마다 0~2가 반복되어 선언 PK에서 7,200건 중복 | `[팀 잠정]` Generator가 계산한 전역 순서대로 Step 1은 0~2, Step 2는 3~5로 보정하고 기존 PK 유지 |
| Summary 알람 시각 | 47건 모두 `occurred_at`이 비어 날짜 조회에서 누락 | `[팀 잠정]` 동일 `(lot, wafer, chamber)`의 `lot_history.track_in_at`으로 채움 |
| 계측 시각 | 48건 모두 `measured_at`이 비어 공식 생성 기준이 없음 | NULL로 유지하고 시간 순서 판정에는 사용하지 않음 `[멘토 확인]` |
| `fault_code` | 600건 모두 NRM이나 최신 전제는 공개 정답 없음 | 원본에는 보존하되 canonical API·모델 feature·평가 입력에서 제외 |
| 제공 조치 48건 | 실제 알람 incident와 직접 대응하지 않는 행이 다수 존재 | raw/reference에만 보존하고 Agent runtime DB는 조치 0건에서 시작 |
| Generator·HTML | 주입 위치와 원인·조치 Mock이 노출됨 | 수신 원본은 불변 격리. corrected generator의 label은 별도 합성 evaluation artifact에서만 사용하고 model feature·threshold 산정·Runtime·Agent 입력에서는 제외 |

### 3.4 개발 DB 운영

- 팀 개발·검증 DB는 모두 학원에서 제공한 공용 PostgreSQL 서버를 사용하며 개인 로컬 DB는 구성하지 않는다.
- 같은 서버 안에 `kosa_agent`(개발·시연), `kosa_agent_e2e`(통합·복구 테스트), `kosa_text2sql`(불변 query reference snapshot) 논리 DB 3개를 분리한다. 앞의 두 DB에는 runtime profile을 적용하고 `action_history=0`으로 시작한다. evaluation profile은 `kosa_text2sql`에만 적용하며, 제공 48건은 `action_history` 컬럼이 아닌 profile metadata의 `fixture_type=MOCK`으로 표시한다.
- 세 DB는 같은 source/corrected file manifest를 공유하되 bootstrap profile·가변 상태가 다르므로 전체 DB hash가 같다고 가정하지 않는다. manifest는 `format_version=3`, `artifact_type`, `dataset_epoch`, `correction_version`, `hash_algorithm`을 필수로 기록하고 DB artifact에는 `profile=runtime|evaluation`을 추가한다. 시연 Backend는 `kosa_agent`만 필수로 연결하고 E2E·평가 DB는 관리 명령에서만 사용한다.
- 기존 구 데이터 DB를 즉시 덮어쓰지 않고 신규 clean base용 DB에서 bootstrap을 검증한 뒤 연결 대상을 전환한다.
- 공용 DB의 schema/data 초기화·migration·Neo4j 전체 재적재는 작업 전 팀에 알리고, 단독 개발 중에도 대상 host·database를 확인하는 guard를 통과해야 한다.
- raw `master.cypher`의 `MATCH (n) DETACH DELETE n`은 공용 Neo4j에 직접 실행하지 않는다. 빈 대상이 아니면 fingerprint·팀 공유·복구 가능한 백업·명시적 교체 확인을 모두 요구한다.
- `kosa_text2sql` 같은 별도 DB가 유지되더라도 Fault Gold DB가 아니라 SQL 회귀용 immutable reference snapshot으로 정의한다.

## 4. 변경된 시스템 흐름

```text
신규 원본 ZIP 검증
  → corrected copy 생성·manifest 기록
  → PostgreSQL·Neo4j·문서 적재
  → Trace 요약 재계산
  → 규칙 기반 evaluation·알람 생성
  → 비지도 이상감지 점수 산출·합성 평가셋 검증
  → 실제 알람을 incident 단위로 집계
  → Neo4j 관계·RAG 문서·계측 결과 조회
  → LangGraph Agent가 원인 가설과 조치 근거 생성
  → 규칙 함수가 base action 결정
  → 검증된 모델 신호가 Summary-only MONITORING을 WARNING으로만 제한적 상향
  ├ MONITORING: 외부 호출 없이 종료
  ├ WARNING: n8n 이메일 전송 후 종료
  └ EQP_HOLD: action·approval 커밋 → 승인요청 이메일 즉시 → HITL 승인·반려
       ├ 승인: MES Mock 어댑터 호출
       └ 반려: MES 미호출
  → 감사로그·대시보드·Text2SQL 조회
```

## 5. 역할별 기능 재기획

### 5.1 A — Detection·Dashboard

#### 유지

- Trace → Summary 재계산
- raw point 및 summary 기반 규칙 판정
- R03 연속 이상 판정
- 알람·Trace·대시보드 API와 React 연결
- IsolationForest 기반 비지도 이상 점수 생성

#### 변경

- `fault_code != NRM`을 정답으로 사용한 Precision·Recall·F1 평가는 삭제한다.
- 고정 임계값 `0.62`는 신규 데이터의 확정 기준으로 승계하지 않는다.
- `anomaly_score`는 0~1 보조 신호로 제공하며, 활성화 조건을 통과한 경우에만
  Summary-only incident의 `MONITORING → WARNING` 한 단계 상향에 사용한다.
- `is_anomaly`와 `T_warning`은 train LOT의 점수 분포에서만 산정하고 모델 manifest에
  score method·quantile method·threshold version과 함께 기록한다.
- score는 base action을 낮추지 않으며, 단독으로 incident·`EQP_HOLD`·HITL을 만들지 않는다.

#### 실데이터 라벨 없는 평가 기준

- 동일 data·seed·feature·모델 버전에서 score와 순위 재현
- LOT 단위 분할과 입력 누수 0건
- score 분포, 상위 K 표본, threshold별 선택 비율 보고
- 규칙 알람·metrology PASS/FAIL과의 연관성 분석(정답률로 표현하지 않음)
- 모델 실행 전후 규칙 알람 불변
- 별도 비공개 Gold 또는 합의된 전문가 라벨셋이 생길 때만 실제 데이터 P/R/F1 평가 추가

#### 팀 합성 평가셋

- 수신 ZIP과 원본 Generator는 hash와 함께 불변 보관하고, 수정 코드는 corrected generator로 분리한다.
- 합성 주입 조건과 label은 Runtime DB·모델 feature·Agent Tool 입력에 넣지 않고 evaluation
  artifact에만 저장한다.
- train·evaluation은 LOT·seed를 분리하고, threshold는 synthetic evaluation label을 보지 않고
  train LOT 점수 분포에서만 정한다.
- 평가 artifact에는 `ground_truth_available=true`,
  `label_source=SYNTHETIC_GENERATOR`, `production_ground_truth_available=false`를 기록한다.
- 합성 지표는 pipeline·모델 비교와 action gate 활성화에만 사용하고 실제 공정 성능으로 표현하지 않는다.

#### 신규 규칙 계산 축

- raw point가 고정 USL·LSL을 벗어나면 Trace OOS 후보로 계산한다.
- Trace를 `(lot_hist_id, parameter_id, recipe_step_no)` 단위로 집계해 mean·std·min·max·count를 재계산한다.
- `evaluation`의 IN·OOC·OOS는 신규 가이드의 window 판정식으로 재현한다.
- Summary OOC는 동일 `(chamber, parameter, recipe step)`에서 `evaluation.alarm_type != 'OOS'`인 표본의 mean 분포로 CL±3σ를 계산한 뒤 Summary mean을 판정한다.
- 제공 파생 CSV와의 일치는 계산 구현의 reference output 검증이며, 현실 Fault를 맞혔다는 의미가 아니다.

### 5.2 B — Neo4j·RAG

#### 유지

- 설비·챔버·파라미터·공정 관계 조회
- 관련 문서 검색 Tool과 근거 반환
- 관계·문서 검색 API와 React 연결

#### 변경

- 기존 RAG 문서의 R02·R03·고정 설비 상하류·LOT_HOLD 표현을 신규 가이드와 대조해 수정한다.
- 수정 전 문서는 최종 임베딩 대상으로 사용하지 않는다.
- Fault 정답을 문서 검색 평가의 정답으로 사용하지 않는다.

#### 평가 기준

- 팀이 문서 내용에서 독립적으로 작성한 검색 질문셋의 Recall@K·MRR
- Neo4j master에서 계산 가능한 관계 질의 정답률
- Agent 답변이 인용한 `chunk_id`·`relation_id`·`corpus_revision`·`graph_revision`이 실제 조회 결과에 포함되는지 검증

### 5.3 C — LangGraph Agent·HITL·n8n

#### 유지

- LangGraph State·Node·Edge와 Tool 호출 예산
- evidence 수집, 구조화 출력, 감사로그
- 조치 결정, 승인·반려·재개, 전송 멱등성
- Agent 실행·승인·조치 API와 React 연결

#### 변경

- FOC/RFM/MFD/TMD를 공개 정답과 비교하는 51건 Accuracy·Macro-F1 평가는 삭제한다.
- Agent의 Fault 출력은 `정답 분류`가 아니라 `predicted fault hypothesis`로 정의한다.
- 후보 Fault Enum은 신규 가이드의 `FOC | RFM | MFD | TMD | OTH`를 사용한다.
- 기존 필드명을 당장 유지해야 한다면 API 설명에서 예측값임을 명시하고, 차기 계약에서 `predicted_fault_code`로 전환한다.
- 제공 `action_history` 48건과 기존 `ACT-0001~0010`을 Agent 정답으로 사용하지 않는다.

#### 라벨 없는 평가 기준

- Pydantic 구조화 출력 성공률과 1회 교정 성공률
- 주장별 alarm·parameter·document·relation 근거 ID 존재 여부
- 같은 입력·설정에서 조치 코드와 필수 근거의 일관성
- 규칙 함수의 양성·음성·경계 fixture 통과
- incident당 실행·조치 중복 0건
- EQP_HOLD 승인요청 이메일은 action·approval 커밋 후 1회, MES Mock은 승인 전 0회·승인 후 1회·반려 후 0회
- 팀 또는 멘토의 블라인드 표본 리뷰 결과. 공개 Gold가 생길 때만 분류 성능 지표 활성화

### 5.4 D — Text2SQL·동적 분석

#### 유지

- 자연어 → 읽기 전용 SQL → 표·통계·차트 구조화 출력
- SQL 안전 검증, 운영/평가 pool 분리, 질의 이력
- Analytics 화면과 평가 artifact

#### 변경

- 기존 데이터 수치가 들어간 12문항의 SQL·기대 결과는 폐기하고 신규 corrected DB에서 다시 작성한다.
- Fault 정답을 요구하는 질문은 versioned Text2SQL 회귀 질문셋에서 제외한다.
- 신규 컬럼명과 enum(`parameter`, `alarm_type`, 3단계 action)에 맞춰 allowlist·질문·차트를 갱신한다.

#### 평가 기준

## 6. 업무 규칙 잠정 기준

### 6.1 알람과 incident

- `[자료 확정]` Trace 알람과 Summary 알람은 신규 자료의 서로 다른 알람 소스다.
- 기존 단일 `fdc_alarm` FK를 재사용하지 않고 `AlarmRef { source, alarm_id }`를 공통 식별자로 사용한다.
- `source`는 최소 `TRACE | SUMMARY | R03`를 구분하며, Agent 실행과 알람의 연결 키는 `(agent_run_id, source, alarm_id)`로 설계한다.
- `[팀 잠정]` 실제 Trace 또는 Summary 알람이 하나 이상 존재하는 `(lot_id, chamber_id)`를 incident로 묶는다.
- 제공 action 48건을 incident 목록으로 사용하지 않는다.
- `[팀 잠정]` 자동 배치는 Detection 완료 뒤 incident마다 Agent 실행 1건을 생성한다.

### 6.2 R03

- `[팀 잠정]` key는 `(chamber_id, parameter_id, recipe_step_no)`이다.
- 처리 순서는 chamber 누적 처리 순서를 사용하고 LOT 경계를 넘어 계산한다.
- 비OOS에서 연속 횟수를 초기화한다.
- `run == 3`이 되는 시점에만 1회 생성하고 4번째 이후에는 중복 생성하지 않는다.
- 경계의 세 번째 OOS가 속한 LOT·챔버 incident에 귀속한다. `[멘토 확인]`

### 6.3 조치 3단계

| 조건 | 조치 | 승인 | 외부 실행 |
|---|---|---|---|
| Summary OOC만 존재, 모델 신호 비활성·미검증·threshold 미만 | `MONITORING` | 자동 | 외부 호출 없음 |
| Summary OOC만 존재, 검증된 incident score가 `T_warning` 이상 | `WARNING` | 자동 | 이메일 |
| Trace OOS가 있으나 R03 없음 | `WARNING` | 자동 | 이메일 |
| R03 존재 | `EQP_HOLD` | HITL 필수 | 신규 가이드상 승인요청 이메일 즉시, 승인 후 MES Mock |

위 매핑은 개발을 계속하기 위한 `[팀 잠정]` 정책이며, 팀 회의와 후속 자료 검증 결과를
`ActionPolicy` version으로 반영한다. 외부 답변은 참고 입력이며 구현 중단 조건으로 사용하지 않는다.
기존 `MONITOR/NOTIFY/LOT_HOLD/EQP_HOLD` 4단계 Enum은 신규 코드에서 사용하지 않는다.

모델 신호를 적용하기 전 base policy는 실제 알람 incident 10개를 `MONITORING 5 / WARNING 2 / EQP_HOLD 3`으로 나눈다. 이는 개발 중 함수 회귀 검증에 사용할 수 있는 versioned regression fixture이지 실제 조치 정답이나 모델 성능 Gold가 아니다. 모델 신호를 활성화한 최종 조치 건수는 model·threshold version에 따라 달라지므로 고정 수용값으로 사용하지 않는다.

### 6.4 anomaly score

- 모델은 WAFER(`lot_hist_id`)별 `anomaly_score`, model·score version, threshold가 확정된 경우
  `is_anomaly`를 반환한다.
- incident score는 포함 AlarmRef를 `lot_hist_id`로 해석하고 중복 제거한 뒤, 같은 model version의
  유효 score 중 최댓값으로 집계한다. 선택된 `lot_hist_id`, member 수, coverage, model·threshold
  version을 조치 근거에 기록한다.
- score가 없거나 model·threshold version이 맞지 않거나 coverage가 부족하면 base policy를 그대로
  적용한다. score는 조치를 낮추지 않고 Summary-only `MONITORING`만 `WARNING`으로 상향할 수 있다.
- score만으로 알람이 없는 incident를 만들거나 `EQP_HOLD`·HITL을 유발하지 않는다.
- action gate는 별도 seed·LOT의 합성 평가셋에서 LOT 누수 0, 같은 bundle score·순위 재현,
  정상 FPR 5% 이하, 주입 anomaly Recall 80% 이상, action fixture 100%를 통과하고
  `MODEL_SIGNAL_ENABLED=true`인 policy version에서만 활성화한다. 이 수치는 실제 공정 성능 목표가
  아닌 `[팀 잠정]` 합성 benchmark gate다.
- 합성 label은 evaluation 전용이며 공개 Fault 라벨·Runtime feature·Agent 근거로 사용하지 않는다.

### 6.5 n8n·MES

- 실제 범위는 이메일 발송까지 구현한다.
- MES 호출은 외부 시스템 연동이 아닌 Mock Webhook/adapter로 분리한다.
- `[자료 확정]` 신규 가이드는 `MONITORING` 외부 호출 없음, `WARNING` 이메일, `EQP_HOLD` 승인요청 이메일 즉시 발송과 승인 후 MES Mock을 제안한다.
- `[팀 잠정]` 현재는 이메일 경로까지 실제 구현하고 MES는 비활성화 가능한 Mock adapter로 작성한다. 기존 멘토링의 이메일 한정 범위와 다르므로 최종 범위는 `[멘토 확인]`으로 남긴다.
- 하나의 action에 EMAIL과 MES가 순차적으로 발생할 수 있으므로 전송 이력은 `action_id` 단일 키가 아니라 `(action_id, channel)` 단위로 상태·시도 횟수·시간·payload hash를 관리한다.
- 승인 전 실제 MES 또는 MES Mock 호출은 금지한다. `EQP_HOLD` 승인요청 이메일은 action·approval 커밋 후 즉시 1회 발송하고, 승인 후에만 MES Mock을 호출한다.

### 6.6 Runtime 스키마 전환

- 신규 base schema에는 기존 `agent_run`, `agent_tool_call`, `approval_request`, `audit_log`, `document`, `document_chunk`, `nl_query_log`, 통합 `fdc_alarm`이 없다.
- 기존 `001_agent_runtime.sql`의 ALTER·backfill·FK를 그대로 적용하지 않는다.
- 초기화 순서는 `base schema(3 DB, action 0) → 001_reference_extensions.sql(3 DB) → corrected base data(3 DB, action 0) → kosa_text2sql Mock 48 → 002_agent_runtime_clean.sql(runtime 2 DB)`로 고정한다.
- `001_reference_extensions.sql`은 세 DB에 R03·document corpus·`nl_query_log`·통합 View를 공통 생성한다.
- `002_agent_runtime_clean.sql`은 corrected base data 적재 후 `action_history=0`을 확인한 두 runtime DB에만 Agent·승인·감사·channel delivery 구조를 CREATE하며 evaluation DB에는 적용하지 않는다.
- incident 잠금·부분 고유 제약, approval-action 직접 연결, checkpoint 별도 초기화, append-only 감사로그, 전송 멱등성 원칙은 재사용한다.
- 두 신규 알람 테이블에는 기존의 직접 `lot_hist_id` 연결이 없으므로 `AlarmRef`를 실행 문맥으로 해석하는 복합 resolve 규칙 또는 별도 canonical event table을 설계한다. 이를 신규 자료에 원래 존재하는 구조처럼 문서화하지 않는다.

## 7. 화면·API 전환 원칙

- 기존 React 8개 Page 화면은 이미 개발된 자산이므로 멘토 답변 전 삭제하거나 합치지 않는다. 상세·redirect URL pattern은 화면 수와 별도로 관리한다.
- 신규 패키지의 5개 화면은 기능 범위 참고로 사용하고, 기존 8개 화면에 기능을 매핑한다.
- 신규 데이터 필드명(`parameter`, `alarm_type`, 3단계 action)을 canonical 계약으로 두고 기존 명칭은 adapter에서만 한시적으로 호환한다.
- 모델 점수는 nullable로 설계하여 모델이 준비되지 않아도 알람·Trace·Agent 기본 흐름을 확인할 수 있게 한다.
- 화면 차트는 일자 추이는 선형 차트, 챔버·파라미터 비교는 막대 차트를 기본으로 한다.

물리적 화면 수를 신규 자료와 동일한 5개로 제한해야 한다는 답변을 받으면 라우트를 삭제하기보다 먼저 메뉴·화면을 통합하여 기존 URL 호환을 유지한다.
